# 第三阶段：Agent 运行时与协作

## 目标与实现边界

第三阶段在已有工程知识模型和知识操作之上，增加持久化的 Agent 注册、任务分发、上下文组装及协作状态管理。运行时负责约束谁可以领取哪类任务、某次执行基于哪些知识版本，以及执行结果如何进入可追溯的复核与提案流程。

本阶段沿用 Python、FastAPI、Pydantic、psycopg 和 PostgreSQL。Agent 身份、任务、执行过程和上下文保存在数据库中，不依赖进程内队列保存任务状态。新增结构使用后续迁移建立，不改写前两阶段已执行的 SQL 迁移。

实现提供本地可运行的协作机制及确定性演示适配器，没有默认接入外部大模型，也不会依据注册信息执行命令、动态导入代码或访问外部网址。注册角色并不等于已经创建具有自主工程能力的模型服务。

## Agent 职责与契约

注册信息区分职责角色、显式能力、可读取实体类型及可提出修改的实体类型。初始角色用于说明职责，而不是推定组织审批权限：

| 角色 | 主要职责 |
|---|---|
| Product | 需求与业务规则分析 |
| Architect | 架构、接口、数据模型与约束分析 |
| Developer | 实现相关知识与变更建议 |
| Test | 测试知识与验证结果整理 |
| Curator | 知识提案与一致性维护 |
| Orchestrator | 任务协调和状态跟踪 |

任务通过所需能力匹配 Agent，读取上下文和提出修改时还需符合注册范围。角色标签本身不代表已经通过身份认证，也不授予绕过知识语义校验的能力。

注册时应显式提供 `capabilities`、`read_kinds` 和 `write_kinds`。可修订类型必须同时可读，且本阶段不允许 Agent 提出 Project 实体修订。类型范围属于本地运行时协议检查，不能替代共享环境的访问控制。

适配器遵循统一 Agent Contract：

| 方法 | 用途 |
|---|---|
| `get_capabilities()` | 声明适配器可处理的能力 |
| `get_context()` | 获取当前任务的固定版本上下文 |
| `execute_task()` | 执行任务并形成结构化结果 |
| `propose_changes()` | 经第二阶段提案流程提出知识修改 |
| `report_result()` | 报告执行结果，保留任务与上下文关联 |
| `request_review()` | 请求人工复核，记录不能自行确定的事项 |

本地确定性适配器用于验证契约和协作闭环，不将合成输出伪装成真实代码实现、模型推理或测试结果。接入实际模型或工程工具前，应另行确定权限、费用、数据范围和结果验证方式。

## 任务分发与执行保护

任务保留目标、验收条件、所需能力和依赖任务。依赖关系用于表达先后约束，调度不会仅凭自然语言结果将前置任务视为完成。符合条件的 Agent 通过显式领取获得有期限的执行租约。

任务必须包含至少一项验收条件。输入知识使用 `{ "id": "<实体 UUID>", "version": 1 }` 固定版本；输入版本与前置任务均不得重复。最大领取次数默认 3，允许范围为 1～10。租约默认 60 秒，可设置为 5～3600 秒。

租约标识把某次执行与后续回报绑定，防止超时或已被替换的旧执行方继续写回结果。心跳用于续租；超时、失败和重试受到次数限制。租约是执行协调机制，不是用户或组织身份认证。

任务状态覆盖创建、就绪、运行、提案、校验、完成、失败、阻塞、待人工复核和取消。需要人工处理的任务保留原因，并通过明确动作恢复；任务不会仅因时间流逝而被默认批准。状态变化与执行记录可追溯。

```text
CREATED → READY → RUNNING → PROPOSED → VALIDATING → COMPLETED
                    │           │
                    │           └─ 校验失败 → NEEDS_HUMAN_REVIEW
                    ├─ 执行失败 → READY（仍有次数）／FAILED（次数耗尽）
                    ├─ 缺少条件 → BLOCKED
                    └─ 需人工判断／上下文陈旧 → NEEDS_HUMAN_REVIEW

BLOCKED／NEEDS_HUMAN_REVIEW → 显式 ready → READY
任意非终态 → 显式 cancel → CANCELLED
COMPLETED／FAILED／CANCELLED 为终态
```

调度采用拉取方式，没有后台扫描器自动回收租约。下一次匹配领取时，过期的运行任务才会被重新领取，或在次数耗尽时标为失败。前置任务必须全部处于 `COMPLETED`，候选任务才可领取；仅创建或标为 `READY` 不会绕过此约束。

创建任务时只能引用已经存在、属于同项目的前置任务；任务定义和依赖一经创建不可原地修改，因此不能通过后续改边制造依赖环。需要改变目标、输入版本或依赖时创建新任务，并按需要取消旧任务。

领取成功会返回 `task` 和仅本次返回的 `lease_token`。任务查询、历史与事件流不公开租约令牌或其摘要。心跳和执行报告携带 `agent_id`、`lease_token` 及最新 `expected_version`；心跳也会追加任务事件并改变任务版本，执行方必须采用响应中的新版本。禁用 Agent 后，该 Agent 不能继续领取、续租或报告。

## 统一上下文与版本

任务执行使用统一组装的 Context Package，而不是由每个 Agent 随意拼接不同版本的知识。上下文记录知识实体和关系的适用版本、来源及证据引用，并保留组装时间和内容摘要。

组装按项目边界、Agent 可读类型及规模限制取数。起始知识使用任务明确指定的版本；关系展开保留关系记录的端点版本，避免把旧关系错误解释为已验证最新内容。同一身份的不同内容版本可以同时出现在上下文中。

上下文是不可变的执行输入记录。后续知识变化不会改写旧包，运行时通过陈旧检查判断其基线是否仍适用。陈旧提示不等于旧知识从历史上变成错误，但提交新结论或复核任务时必须显式处理版本变化。

陈旧检查覆盖已装入包或作为证据依据记录的实体／关系版本及其状态，不侦测组装后新增加、从未纳入该包的图谱边。它不是全项目快照或任意知识变化的订阅机制。需要更新已固定的任务输入时创建新任务；只把旧任务重新放回队列不会自动改写种子版本。

上下文默认展开深度为 2，允许范围为 0～3；默认最多包含 100 个实体版本，允许范围为 1～200；关系上限为 1000，编码后内容上限为 1 MiB。同一身份的不同版本分别计数。达到图谱规模边界时返回 `truncated`，调用方不能将截断包视为完整项目知识；内容超过字节上限会被明确拒绝。

证据继续固定到具体版本。可读范围内的证据内容可以随上下文收集；证据链不会增加图谱展开深度，但仍受实体数量和内容大小限制。包中的 `baselines` 用于与当前知识比较，`sha256` 标识按确定格式编码后的包内容；它不代表外部来源真实性已被核验。

## 结果、人工复核与知识提案

任务输出与正式知识分开保存。Agent 可以回报结果和提交候选修改，但不能通过任务完成动作自动批准或提交正式知识。

执行报告通过 `outcome` 区分成功、失败、阻塞与请求复核，并记录 `summary`、结构化 `artifacts` 及逐项验收声明。`criterion_index` 从 0 开始对应任务验收条件；`passed` 是执行方声明，可附固定版本的证据。结构化产物只保存 JSON，运行时不执行其中的脚本或抓取其中的网址。只有成功报告可以携带待审核的知识修订。

单次结构化产物最多 256 KiB，并且必须是有效 UTF-8、只含有限数值的 JSON。Agent 变更或验收声明所引用的证据也必须来自上下文已经加载或已列出的固定版本证据引用，不能注入任意上下文外证据。关系的新适用版本只能是原上下文固定版本，或同一提案中对应实体修订后的下一版本。

知识修改复用第二阶段提案、语义校验和审核历史，继续遵守实体范围、生命周期、关系方向、证据要求与乐观并发保护。Agent 的知识提案仍需明确审核和提交；运行时不会因为调用方宣称任务成功，就将推断提升为事实。

人工复核用于处理不确定性、冲突、缺失信息及需要负责人判断的事项。复核署名和原因用于追溯，不代表 MVP 已经实现组织鉴权或审批职责分离。

任务结果先进入 `PROPOSED`，管理方显式校验后才可进入 `VALIDATING`。校验检查上下文是否仍适用、所有验收条件是否都有通过声明，并在存在知识提案时复用第二阶段试运行校验。它没有实际运行外部代码或测试。确认完成也必须显式调用；如果任务关联知识提案，该提案应先经第二阶段接口明确提交。

任务提案只允许修订上下文中精确版本的已有知识，并受 Agent 的 `write_kinds` 限制；修订关系时两端实体类型都必须可写。运行时将 Agent 提案的署名设置为 Agent 身份，知识性质设置为 `inference`，不能借执行报告自行声明事实。新知识实体创建仍通过前两阶段已有入口处理。

完成检查会认可该任务提案自身已提交的版本变更，同时拒绝无关的后续修改；任务完成不会把过期上下文无条件视为最新。发生冲突后需人工处理已提交知识及任务，不会自动撤销历史提交。

## 事件协作

运行时提供可分页轮询的事件流，使调用方能够跟踪任务状态变化并协调后续动作。事件记录是数据库中可追溯的协作信息，不等同于已经部署消息中间件、推送通知或外部 webhook。

使用事件游标时，调用方应保存消费进度并容忍重复读取；业务动作仍须遵守任务版本与租约约束，不能仅凭收到一次事件就假设有权执行写入。

事件流按 `project_id` 读取，`after` 是该项目已消费的事件游标，返回 `next_cursor` 和 `has_more`。读取与项目内任务写入共用事务锁，避免尚未提交的较小事件编号被同项目游标越过。游标应按项目分别保存；没有新事件时不会推进游标。轮询本身不会派发外部通知，也不是阻塞式推送订阅。

## 启动与演示

依赖和服务启动方式沿用项目使用说明。已有数据库需执行：

```sh
python -m knowledge.db
```

迁移完成后启动 API，交互式接口文档位于 `/docs`。运行合成协作演示：

```sh
python -m knowledge.runtime_demo
```

演示通过 HTTP 使用两个有依赖关系的任务：执行方领取并读取上下文，确定性适配器形成候选产物，管理方校验并经第二阶段明确提交知识提案，再确认任务完成，使后续任务可领取。代码使用 `AgentAdapter` 协议和 `DemonstrationAdapter`；它们位于 `knowledge/runtime_contract.py`，不代表已经接入真实 Product／Architect／Developer／Test 模型。

### 注册与任务示例

向 `POST /runtime/agents` 提交：

```json
{
  "project_id": "<已有项目 UUID>",
  "name": "产品知识演示 Agent",
  "role": "Product",
  "capabilities": ["demo.refine"],
  "read_kinds": ["Requirement", "BusinessRule", "Evidence"],
  "write_kinds": ["Requirement"],
  "actor": "本地维护者"
}
```

同一项目内 Agent 名称唯一。注册身份、角色、能力和范围不可原地修改；`POST /runtime/agents/{agent_id}/state` 使用 `expected_version`、`actor`、`reason` 和 `status`（`active` 或 `disabled`）追加启用状态事件。

向 `POST /runtime/tasks` 提交明确任务：

```json
{
  "project_id": "<项目 UUID>",
  "title": "补充订单取消需求说明（合成示例）",
  "goal": "基于指定知识版本提出说明修订，不能直接改变正式知识",
  "required_capability": "demo.refine",
  "acceptance_criteria": ["修订明确标注为合成示例，并经过人工审阅"],
  "input_knowledge": [{"id": "<已有需求 UUID>", "version": 1}],
  "dependencies": [],
  "max_attempts": 3,
  "actor": "本地维护者"
}
```

任务初始为 `CREATED`。管理动作 `/ready`、`/cancel`、`/validate`、`/complete` 都采用以下请求结构；每次取刚读取的任务 `version`，不要将示例中的 1 固定用于后续操作：

```json
{
  "expected_version": 1,
  "actor": "本地维护者",
  "reason": "审阅任务目标后显式放入待领取队列"
}
```

### 领取、报告与确认

执行方向 `POST /runtime/claim` 提交 `agent_id`，可选 `task_id` 和 `lease_seconds`。不指定任务时按创建顺序寻找可执行任务。没有可领取任务时返回 `task: null`；不代表所有任务都已完成，还应关注依赖和复核状态。组装上下文失败的候选会进入待人工复核状态，避免阻塞其后的可执行任务。

领取响应中的 `lease_token` 仅返回一次。读取 `/runtime/tasks/{id}/context` 获得不可变上下文包后执行任务，再向 `/runtime/tasks/{id}/report` 报告。例如不携带知识修改的合成结果：

```json
{
  "agent_id": "<Agent UUID>",
  "lease_token": "<本次领取的令牌>",
  "expected_version": 3,
  "outcome": "succeeded",
  "summary": "已根据固定上下文形成合成演示结果，待人工复核",
  "acceptance": [{"criterion_index": 0, "passed": true, "evidence": []}],
  "artifacts": {"synthetic": true},
  "changes": []
}
```

版本 3 只是示意，实际应使用最近领取或续租响应中的版本。`outcome` 也可为 `failed`、`blocked` 或 `review`。`changes` 使用第二阶段已有对象修订结构；成功报告带变更时，运行时原子创建关联提案，返回的任务 `runtime.proposal_id` 可用于查询。

报告成功不等于任务完成。管理方先调用任务 `/validate`；若包含提案，校验会同时试运行提案并更新其事件版本。确认后读取最新提案，向第二阶段 `/operations/proposals/{id}/commit` 显式提交；最后以最新任务版本调用 `/complete`。无知识提案的任务无需第二阶段提交，但仍需校验和明确完成确认。

### 查询、事件及错误

任务与 Agent 列表使用 `project_id`，支持 `limit`（1～200，默认 50）和 `offset`（默认 0）；任务列表还可用 `status` 筛选。任务历史按事件版本从新到旧分页。上下文接口返回最近一次领取对应的包，历史包本身不会被修改。

`GET /runtime/events?project_id=…&after=0&limit=50` 按事件编号升序返回一页任务事件，下一次采用响应的 `next_cursor`。`limit` 范围为 1～200；`has_more` 为真时应继续读取。该流不包含所有知识变更，也不包含全部 Agent 状态事件。

常见状态码仍为：结构／语义无效 422、身份不存在 404、并发版本或租约冲突与无效状态迁移 409。上下文陈旧、声明未通过或提案试运行失败，也可能体现为成功响应中的任务状态转为 `NEEDS_HUMAN_REVIEW`，必须读取任务状态与 `runtime.review`，不能只依据 HTTP 200 判断任务可完成。

## 待负责人确认的决策

- **实际 Agent 与工具：** 使用哪些模型、执行环境、代码仓库与工具，何时允许调用，以及如何限制成本和数据流出，目前没有默认绑定。
- **身份与权限：** 调用方提供的操作者、Agent 注册及复核署名仍属于本地声明。共享使用前需要确定认证方式、角色权限、项目访问规则和是否分离提案人与审批人。
- **能力与任务策略：** 能力标签和通用状态是工程默认机制。具体产品、架构、开发及测试 Agent 的职责边界、验收标准、重试和升级规则需结合真实场景确认。
- **上下文策略：** 可读取类型、展开深度和内容限制需要随实际项目评审；不能将可达关系自动视为业务上的权威依据。
- **结果与审批：** 哪些任务结果必须人工复核、哪些证据足以确认完成、由谁批准正式知识，仍需项目负责人决定。

## 本阶段不包含

第四阶段的端到端 AI 原生 SDLC 自动流水线仍未实现，包括自然语言目标自动分解为完整研发流程、自动修改和发布业务代码，以及跨外部系统执行部署。第三阶段交付的是可以验证的运行时与协作底座。
