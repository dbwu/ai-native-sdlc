# 工程知识模型演进设计

M0 交付只读类型注册表和原文证据定位。后续类型按实际的需求分析、设计、实现与验证场景扩充。软件工程图使用已确认的模型及其固定版本作为输入，质量与行为模型先在选课案例中验证，再用于工程视图。模型清单依据[前期设计讨论](https://chatgpt.com/share/6af28cfe-329c-83ec-944a-18d28f3ac9e4)。

## 调整后的里程碑

M1 已提供普通文本／Markdown 语义抽取、固定原文证据、候选编辑和人工审阅。M2 在此基础上提供去重与冲突建议、增量比较、逐项裁决及固定版本影响追溯。页面与导出继续采用 Mermaid，暂不引入 Structurizr。M3 的首要目标为架构和 UML 的图形差异审阅，Structurizr 保留为明确需要 C4 多层视图时的可选适配。PlantUML 在需要相应 UML 图种时再评估。

| 里程碑 | 交付内容 | 与变化标记的关系 |
|---|---|---|
| M0 | 类型注册表、不可变来源快照和原文定位 | 固定知识的类型与依据 |
| M1 | 配置模型生成需求、业务规则、领域候选，逐项审阅并形成知识提案 | 保留来源键、知识 ID、验收条件键、引用版本及原始模型交互，补充图形元素稳定键 |
| M2 | 去重候选、冲突检查、增量匹配和影响追溯 | 区分身份延续、新增、修订、删除建议与受影响对象 |
| 行为与质量试点 | 先固定活动和消息，再固定质量场景、指标与测量 | 给活动、时序和质量分析提供可审阅的语义模型，可与 M2 并行 |
| M3 | 先实现修改前、修改后、左右对照及变化叠加，再扩展图种和可选渲染器 | 统一展示增删改、重命名、归属移动及有依据的影响标记 |
| M4 | 从固定代码快照反向提取实际接口，与已确认设计对照 | 追踪设计变化与实现变化，并关联测试证据 |

M1 的实现边界和选课操作步骤见[文档知识抽取与审阅](m1-knowledge-extraction.md)。文字层 PDF、DOCX 解析在普通文本闭环验证后补充，解析后仍需冻结规范化文本并保存页面／段落与原文位置的映射。扫描件 OCR 和自动跨来源合并不属于本轮。

M2 的具体使用与边界见[知识增量、冲突审阅与影响追溯](m2-incremental-review.md)。缺失或模型提出的移除在本轮作为审阅建议记录，实际归档／退役继续使用独立的生命周期修订提案；不自动删除。语义检查基于有界召回，不承诺发现全项目全部冲突。

M3 首版已将基线对照接入项目知识页。架构、泳道和时序图支持原版查看、左右对照和增删改叠加。选课三轮和历史消息的比较边界见 [M3 操作与验收](m3-diagram-comparison.md)。

## M0 的可用能力

升级已有数据库时，先按[项目启动说明](../README.md)应用迁移 `012_source_text_snapshots.sql`，再启动工作台。

`GET /metamodel/registry` 从后端的实体属性定义和关系规则提供当前支持的类型、属性、关系端点及相关约束。工作台「项目知识」提供「类型注册表」入口，原有调用方仍可使用 `GET /metamodel`。下文列出的新增模型是演进计划。当前实体与关系修订继续使用元模型版本 `1`。

原文证据引用指定来源的**固定修订**，定位信息随 `Evidence` 修订存储在 `attributes.extensions.source_span`。`source_id` 和 `source_version` 定位快照，`sha256` 是快照原文按 UTF-8 编码后的内容摘要。`start` 和 `end` 使用从零开始的 Unicode 码点偏移，区间为左闭右开。`quote` 必须与这段切片完全一致，空白和换行均按已保存原文计算。原文引用记录文档写了什么，适用性仍由审阅人确认。

| API | 用途 |
|---|---|
| `POST /operations/source-snapshots` | 按项目、来源 URI 和外部版本登记纯文本或 Markdown 原文，以 `text` 格式保存为不可变来源修订。 |
| `POST /operations/source-evidence/proposals` | 用原文定位和指定的实体或关系修订建立证据提案。经现有提案流程校验与确认后，证据关联到新的知识修订。 |
| `GET /operations/projects/{projectId}/source-evidence?table=entity&id={id}&version={version}` | 读取指定知识修订的原文证据。使用 `table=relationship` 查询关系修订。 |
| `GET /operations/sources/{sourceId}/versions/{sourceVersion}` | 读取证据引用的原文修订。工作台在其中高亮固定区间。 |

使用时，在「项目知识」选中一条需求或知识，查看「原文证据」。当前可修订版本可展开「登记原文并提出证据」，填写来源 URI、来源版本、原文、证据引文、操作署名和提案依据，再点击「提出证据提案」。引文出现多次时，可扩展到包含上下文的唯一片段。审阅人校验并确认提交后，返回该知识的新修订并点击「查看原文」。旧记录按当时保存的关联显示，历史证据仍指向原来的原文修订。

## 十类知识模型的演进

知识实体和关系保留稳定 ID 与不可变修订。随父记录一起审阅的结构化子项使用父 ID、父修订版本和稳定子项键定位，例如验收条件、流程步骤和数据字段。需要跨对象引用且具有独立审批或生命周期的知识再设独立实体，例如跨需求共享的用例、独立维护的接口契约。历史引用始终以保存的版本为准。M0 的证据提案绑定实体或关系修订，子项级证据在对应结构化模型落地时加上子项键。

| 分类 | 当前可复用的结构 | 建议补充及落地顺序 |
|---|---|---|
| 需求 | `Requirement`、功能／非功能分类和文本验收条件 | 在选课试点引入 `AcceptanceCriteria` 的稳定子项键，再补 `UseCase`、`Scenario`，使验收和测试可追溯到具体条件。 |
| 领域 | `Domain`、术语表与模块归属 | 随有明确业务对象和边界的项目引入 `Aggregate`、`ValueObject`、`DomainEvent`。优先验证业务身份、归属和事件来源。 |
| 行为 | `BusinessProcess`、流程步骤、条件分支和时序场景 | 在 M3 前落地 `Activity`、`InteractionScenario`，固定责任、消息和规则引用。对象生命周期用 `State`、`Transition` 表示。 |
| 架构 | `ArchitectureComponent`、组件依赖和项目模块目录 | M3 先复用领域／模块模型实现图形差异。需要 C4 视图时补显式系统及 `Container` 运行边界，`Module` 按实际模块结构演进。组件交互需要端口和适配器边界时增加 `Port`、`Adapter`。 |
| 数据 | `DataModel` 及 `schema_definition` | 随数据视图补 `DataEntity`、`Field`、`Schema`。有明确读写和传递证据时建模 `DataFlow`。 |
| 接口 | `Interface`、协议、契约位置和设计中的契约属性 | 试点补 `Operation`、`APIContract`，行为模型用 `Message` 引用交互操作，M4 再与实现中观察到的接口对照。 |
| 部署 | 项目架构基线可引用组件知识 | 有部署资料时引入 `Environment`、`Node`、`ServiceInstance`、`Network`，实例指向固定的组件或应用版本。 |
| 安全 | `Constraint`、`Decision`、流程参与者 | 先按明确需求引入 `Actor`、`Role`、`Permission`，再用威胁分析补 `Threat`、`TrustBoundary`。 |
| 质量 | 非功能 `Requirement`、`Decision`、组件与测试关联 | 在 M3 前试点 `QualityAttribute`、`QualityScenario`、`Metric`，先明确指标与验收口径，再记录实际测量。 |
| 测试 | `TestCase`、执行记录和 `test_execution` 证据 | 逐步建模 `TestScenario`、`TestExecution`、`Coverage`，让覆盖关联到验收条件，执行结果固定代码快照和测试版本。 |

## 质量与行为模型的落地顺序

1. **M1 完成基于大模型的文档抽取与审阅。** 复用可配置模型网关，按需求、业务规则和领域概念的结构约束生成候选。服务端核对来源版本、引文区间和关系端点，审阅人核对原文是否支持候选语义。用人工标注的选课样本检查各类候选的准确率、召回率和证据支持率，重点验收否定、例外和边界条件。确认的选课规则与验收条件固定到具体版本。
2. **先落实行为步骤和交互场景。** 复用「提交选课」流程及现有步骤键，给活动绑定责任模块版本和规则版本，给消息绑定参与者及接口操作。按基础选课、容量限制、课表冲突三轮验收。保留重复请求返回原记录的分支，定位余位检查和课表冲突检查的增量。确有对象生命周期时，再记录状态、事件、转移条件与动作。
3. **落实质量场景和测量。** 用 `QualityAttribute` 表示性能、可靠性等维度，用 `QualityScenario` 表达触发条件、运行环境、受影响组件、预期响应和量化阈值。`Metric` 固定单位、统计口径和测量条件。设计追溯可沿 `Requirement → QualityScenario → ArchitectureDecision → Component → TestCase` 查看，实际测量值关联到具体 `TestExecution`。选课的并发测试可验证最后一个名额最多由一个人获得。性能阈值在另有明确需求时按负载和统计窗口单独登记。
4. **M3 从已确认模型生成视图并审阅图上差异。** 领域与模块树读取归属，活动图读取责任方及条件分支，时序图读取场景的有序消息，状态图读取对象的状态和转移。比较固定的原基线与候选设计，或两个已确认版本。先以 Mermaid 验证架构、活动和时序变化，后续图种复用同一份结构化差异。Structurizr 的 C4 适配延后按需评估，届时读取显式系统边界、运行单元和依赖。预览和导出使用同一组固定版本。
5. **M4 闭合设计与实现的核对。** 以 FastAPI 的 HTTP API 为试点，从固定代码快照读取路由和处理函数。具备隔离启动条件时采集应用生成的 OpenAPI，对照已确认接口契约。把静态声明、运行时观察和测试结果各自关联到对应证据，提请审阅新增、缺失或变更的端点。

M2 的去重、冲突和增量审阅可以与行为、质量试点并行。试点需先确认场景、规则和验收口径，M3 才能按同一批知识引用生成并验收视图。

## 图形版本比较的身份约定

知识实体使用稳定 UUID 和不可变修订。领域、模块、步骤和场景沿用已确认的模型键，新增关系、分支和消息允许携带稳定键。验收条件使用父需求 ID、需求版本和条件键定位。修改名称、文字、顺序或归属时保持身份，新增业务对象使用新身份。模型输出的匹配只作为候选，跨来源匹配需要人工确认。

模型键属于相应项目、来源或父对象的命名空间，不把不同来源的同名键自动合并。渲染阶段生成的节点编号和布局坐标仅供画图，不承担跨版本匹配职责。历史消息缺少稳定键时保持原始快照，只提供场景级比较，不按文本相似度或数组位置制造精确对应。

结构化差异保留对象定位、修改前后内容、比较版本、需求与规则引用。同键改名和移动归属分别记录；被删除的节点和连线在将来的比较视图中从旧版本补入。模型内容没有变化、但处于影响路径上的对象使用单独的影响标记。布局变化不记为业务变化，也不使用自动布局后的图片差异判定需求影响。

图形比较的验收按实际变化进行。容量限制可以只修改原选课模块的职责和行为，不要求新增服务或模块。活动图应能定位容量判断和满员分支，时序图应能定位有依据的消息变化。增加时间冲突规则后，容量检查应作为已有内容保留。UML 箭头的业务语义保留，变化通过附加标记或高亮区域表达。

## 选课历史回查验收

1. 在独立验收项目按教学版本 `v1`、`v1.1`、`v1.2` 导入知识并审阅项目基线。操作步骤见[选课三轮基线验收](requirements-design-guide.md#用选课系统验收三轮基线)。
2. 选择容量限制知识的当前版本，给其中一条规则附加原文证据。确认提案后，检查新修订能打开并高亮正确引文，旧知识修订仍可按版本查看。可用含中文和表情符号的原文核对码点偏移。
3. 以同一来源登记下一版原文，再查看第一份证据，核对来源版本、原文摘要和高亮内容仍对应原来的快照。用不匹配的引文或偏移试验，确认系统在入库前拒绝。
4. 切回旧项目基线，对照基础选课流程与容量、课表冲突后续版本。旧图应保留当时确认的分支，Markdown 导出与所选基线版本一致。
