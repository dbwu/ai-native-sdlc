# 第四阶段：AI 原生 SDLC 工作流

## 目标与实现边界

第四阶段把已有知识模型、知识操作和 Agent 运行时组成可追溯的研发流程。工作流按需求、架构、实现和验证阶段组织任务，使后续阶段能够使用前一步已确认的知识版本，而不是在流程开始时固定一套会很快陈旧的输入。

本阶段沿用 Python、FastAPI、Pydantic、psycopg 和 PostgreSQL。新增状态通过后续迁移和不可变事件保存，不修改已经执行的前三份迁移。既有实体、关系、提案和任务接口继续可用。

本地参考场景明确为合成的订单取消示例，用于验证工作流、知识追溯和真实测试执行机制；它不代表项目已经采纳订单系统的业务要求。实际模型服务、Git 仓库、CI 平台、部署目标和组织鉴权没有默认接入。

## 工作流定义

创建请求必须显式选择允许的场景，不能省略选择后自动套用某个业务模板：

```json
{
  "project_id": "<已有项目 UUID>",
  "title": "订单取消参考流程（合成示例）",
  "goal": "验证需求到真实参考测试的可追溯流程，不改写真实业务仓库",
  "scenario": "order_cancellation_v1",
  "input_knowledge": [],
  "max_stage_retries": 2,
  "actor": "本地维护者"
}
```

`input_knowledge` 可补充最多 20 个固定知识版本，使用既有 `{ "id": "<实体 UUID>", "version": 1 }` 结构。`max_stage_retries` 表示每阶段人工重建任务次数上限，默认 2，允许范围为 0～5；它与第三阶段单个任务的租约领取次数分开计数。

## 流程与知识版本

四个阶段分别关注：

| 阶段 | 稳定标识 | 角色／所需能力 | 目标 |
|---|---|---|---|
| 需求 | `requirements` | Product／`sdlc.requirements` | 明确需求、业务规则和验收条件 |
| 架构 | `architecture` | Architect／`sdlc.architecture` | 形成组件、接口和数据模型产物 |
| 实现 | `implementation` | Developer／`sdlc.implementation` | 形成代码内容和对应代码版本的实现证据 |
| 验证 | `verification` | Test／`sdlc.verification` | 形成测试内容及与待验证代码对应的真实执行证据 |

工作流管理阶段先后顺序，Agent 运行时管理具体任务的领取、租约、上下文和结果。后续阶段任务延迟创建，以使用推进时读取的最新知识版本。工作流中的阶段完成不是仅凭一段自然语言结论判断，而是检查关联任务、必要产物及确认状态。

知识修改仍走第二阶段提案流程。Agent 报告产物后，需经过任务校验、关联知识提案的显式提交及任务完成确认，才允许工作流推进。工作流不把 Agent 的成功声明自动提升为正式工程事实。

### 初始化与阶段门禁

创建流程只建立 `DRAFT` 流程记录和初始化提案，不直接写入正式工程知识。初始化提案建立需求、组件、接口、数据模型、代码、测试、代码证据和测试证据八个占位产物；证据起初只是“待确认文档”，关系也为待确认状态。它们不是已实现或验证的事实。流程响应中的 `state.bootstrap_proposal_id` 指向该提案，调用方必须先审阅、校验并显式提交，才能启动。

启动后只创建当前阶段任务。每阶段采用两个相互独立的确认层次：

1. 执行方领取第三阶段任务，读取固定上下文、报告结果并提出知识修订；管理方校验产物、显式提交该知识提案，再确认任务完成。
2. 流程检查已提交产物是否满足当前阶段门槛，生成另一份阶段门禁提案；管理方审阅、校验并显式提交门禁提案，随后才可推进下一阶段。

门禁提案将本阶段已确认产物设为生效，记录人工确认来源，并把模板中的追溯关系重新固定到对应的新知识版本。最终验证门禁只有在内容和执行证据匹配时，才会将需求的实现／验证关系设为已验证。生成门禁提案本身不是提交，也不授予调用方组织审批权限。

阶段产物提案必须恰好修订该阶段声明的输出，不能用缺少产物或夹带其他修订的计划通过门禁。需求阶段要求验收条件，架构阶段要求组件职责、接口协议和数据结构；实现阶段要求当前参考代码及匹配的代码证据；验证阶段要求测试内容和属于当前阶段任务的真实执行记录。阶段报告还须标明对应的 `stage` 与 `scenario`。

所有流程管理的知识都记录版本基线。下一阶段采用前一门禁已提交的版本；额外 `input_knowledge` 仍保持创建请求中固定的版本，不会自动改为新知识。若发生流程以外的并发修改，旧门禁不能直接覆盖新状态，需复核后重试或创建新流程。

暂停、恢复、取消和失败处理保留明确原因及事件版本。恢复或重试不能无提示覆盖已有知识修订；需要重新执行时创建新的阶段任务并保留旧尝试记录。项目边界、预期版本及已有任务约束继续适用。

流程状态与任务状态、知识提案状态分别保存：

```text
DRAFT → 显式 start → RUNNING
RUNNING → prepare_gate → AWAITING_GATE
AWAITING_GATE → 门禁已提交后 advance → 下一阶段 RUNNING／最终 COMPLETED
RUNNING → 阶段失败或质量检查未通过 → BLOCKED
BLOCKED／AWAITING_GATE → 显式 retry → 关系对齐门禁或新阶段任务
RUNNING／AWAITING_GATE／BLOCKED → pause → PAUSED → resume → 原状态
任意非终态 → cancel → CANCELLED
```

重试保留旧任务及其结果，不撤销先前已提交的知识。取消流程时会取消当前尚未终结的任务，不物理删除历史或回滚已提交知识。`COMPLETED` 和 `CANCELLED` 为流程终态。

若失败产物已经提交，或者门禁被拒绝、提交后又遇到外部修改，可以显式 `retry`。旧的待校验或已校验门禁会先留下拒绝记录。若已有关系仍固定在旧实体版本上，流程只生成新的关系对齐提案并停在 `AWAITING_GATE`；人工校验、提交该提案后，`advance` 创建同阶段的新任务，不把对齐操作计作阶段完成。无需对齐时才直接创建新尝试。

`pause` 仅暂停流程推进与可信参考执行，不强制中断或冻结第三阶段已经存在的任务。执行方仍可能完成其已领取任务或回报结果；恢复流程后仍要通过阶段门禁。需要撤回当前任务时使用流程 `cancel`，而不是将暂停当作撤销执行授权。

## 真实参考执行与证据

参考执行器只运行包内允许的受信任场景，不接收调用方任意源码、路径、命令或动态模板。它在临时目录生成实现与独立测试，使用固定 Python 测试命令运行，并记录源码／测试内容摘要、执行结果和有界输出。

当前允许的场景标识为 `order_cancellation_v1`，生成 `order_service.py` 和 `test_order_service.py`。四项独立测试覆盖未支付订单取消、已支付订单拒绝且不改变状态、重复取消幂等，以及不同订单之间的状态隔离。执行超时为 10 秒，标准输出和错误输出分别最多保留 16 KiB，并明确标记日志是否被截断。

测试报告必须与当前待验证代码的内容摘要对应，不能用旧版本测试通过记录证明新代码通过。失败、超时或缺失报告均不能等同于验证成功。执行记录体现本次本地测试实际运行的结果，不保证其他环境、真实生产代码或未覆盖行为同样正确。

临时运行目录在执行结束后清理；需要追溯的源码文本、摘要和结果作为工作流产物保存。参考执行器不是通用沙箱，也不承担运行不受信任上传代码的能力。

## HTTP 使用

已有数据库先执行 `python -m knowledge.db` 应用第四份迁移，然后按项目使用说明启动 API。所有新增流程接口位于 `/workflows`：

服务启动后可运行完整参考演示：

```sh
python -m knowledge.workflow_demo
```

该命令创建独立项目及 Product、Architect、Developer、Test 四个参考 Agent，依次运行四阶段，输出完成状态、真实执行的测试数量、代码／测试摘要及已验证追溯关系。示例中的业务内容与审核署名均为合成数据。命令会自动调用显式审核接口以验证协议，不表示真实负责人已经审批，也不会修改用户业务仓库。

| 方法 | 路由 | 行为 |
|---|---|---|
| GET | `/workflows/templates` | 查看四阶段模板与允许的参考场景 |
| POST／GET | `/workflows` | 创建草稿流程或按项目分页查询 |
| GET | `/workflows/{id}` | 读取定义、阶段、当前任务和门禁引用 |
| GET | `/workflows/{id}/history` | 按版本从新到旧读取不可变事件 |
| GET | `/workflows/{id}/tasks` | 查看阶段关联任务及所有重试 |
| GET | `/workflows/{id}/executions` | 查看真实参考运行、摘要、退出码和有界日志 |
| POST | `/workflows/{id}/reference-executions` | 持有当前验证阶段任务租约时，实际执行内置测试 |
| POST | `/workflows/{id}/actions/{action}` | 显式执行 `start`、`prepare_gate`、`advance`、`pause`、`resume`、`retry` 或 `cancel` |

流程列表支持 `project_id`、`status`、`limit`（1～200，默认 50）和 `offset`（默认 0）。历史记录采用相同分页范围；阶段任务和执行记录读取指定流程的全部相关记录。

### 版本和管理动作

流程管理动作采用以下请求结构：

```json
{
  "expected_version": 1,
  "actor": "本地维护者",
  "reason": "核对已确认产物后显式推进当前流程"
}
```

`expected_version` 必须来自刚读取的流程 `version`。它与阶段任务事件版本、知识内容版本和第二阶段提案事件版本彼此独立；不能把同一个数字用于所有接口。执行参考测试也会追加流程事件，因此执行后应重新读取流程版本，再进行后续管理动作。

阶段任务的领取、上下文读取、结果报告、校验和完成继续调用第三阶段 `/runtime` 接口；初始化提案、Agent 产物提案及门禁提案继续使用第二阶段 `/operations/proposals` 的校验与提交接口。不要只检查某个接口是否返回 HTTP 200，还应读取任务状态、提案校验结果及流程 `state.diagnostic`。

### 可信参考执行

仅在验证阶段，当前阶段任务的有效租约持有方可以向 `/workflows/{id}/reference-executions` 提交：

```json
{
  "agent_id": "<执行方 Agent UUID>",
  "lease_token": "<领取当前验证任务时返回的令牌>",
  "expected_version": 3
}
```

这里的 `expected_version` 是**任务事件版本**，因为它用于检查租约；不是流程版本。示例中的 3 只是占位，应采用最近领取或心跳响应中的实际值。执行前后都会检查租约；到期后不能用旧执行尝试写入证据。

响应是服务端产生的执行记录，其 `id` 可用于验证阶段报告的 `artifacts.execution_id`。调用方不能上传自称通过的报告替代该记录。质量门禁核对流程、阶段任务、代码 ID／版本、源码摘要、测试内容摘要与证据指向；完成阶段归档保存实际采用的执行记录，不仅保存“最近运行过”的记录。

### 常见冲突与恢复

结构或语义无效通常为 422，不存在的身份为 404，预期版本、租约、状态或知识基线冲突为 409。阶段质量未通过时，流程也可能以成功响应转为 `BLOCKED` 并给出诊断；这不代表阶段通过。

初始化提案若被拒绝，不会自动重写该提案；应取消不再使用的草稿流程并用明确的新定义创建流程。进入阶段后的失败或门禁问题可使用显式重试，仍须审阅重试对齐提案。对已提交知识不自动回滚。

## 待负责人确认的决策

- **真实业务流程：** 四阶段划分是初始工程默认值。实际业务的验收条件、产物门槛、角色职责和例外流程需要负责人确认。
- **模型与工具：** 接入哪些外部模型、代码仓库、CI 或部署服务，以及费用、访问授权和数据范围，目前没有默认绑定。
- **执行环境：** 本地内置参考执行不能代替实际项目的受控构建和测试环境。运行外部代码前需明确隔离、依赖、资源和结果收集策略。
- **审批与权限：** 操作者和审核者仍是本地署名声明；共享环境的身份认证、项目权限及提案／批准职责分离尚需单独接入。
- **自动化程度：** 哪些阶段可以自动推进、哪些变更必须人工确认、失败后如何回退或重新规划，不能由通用工作流擅自决定。

## 后续阶段边界

不实现持续运行反馈驱动的知识自动演进、自行修改业务规则、自动发布部署或跨外部系统的闭环自治。工作流的状态可追溯，不表示已经获得执行所有工程动作的授权。
