# M1 文档知识抽取与审阅

本版提供普通文本／Markdown 原文到知识候选的中文页面闭环。复用已配置模型网关、M0 原文证据和既有提案审阅，支持需求、业务规则、领域概念及这些类型之间合法的关系。模型只生成候选，正式知识须经过人工选择、校验和确认提交。

## 启动与模型选择

先运行 `python -m knowledge.db` 应用 `013_knowledge_extraction.sql`，再构建前端并重启应用。抽取与设计、代码生成共用后台任务处理器，默认随 API 启动。独立部署可运行 `python -m knowledge.design_worker`。后台关闭时，页面任务会留在等待状态。

实际部署沿用[需求设计指南中的模型配置](requirements-design-guide.md)。抽取、设计和代码生成共用 `KNOWLEDGE_MODEL_*` 配置，调用兼容 Chat Completions 的模型服务。原文与本项目已有需求、规则和领域知识会发送给所配置的服务。应用不会自动加载 `.env`，应在启动进程中设置环境变量。

本地可以使用已登录的 Codex CLI 做真实抽取验收。开发辅助工具 `tools/codex_validation_bridge.py` 将同一份模型请求交给 `codex exec`，以只读、临时会话返回 JSON。调用沿用本机 Codex 登录状态，不读取或复制登录凭据。默认沿用 CLI 的默认模型，页面中的 `codex-local` 为本地验收接口名称。本地客户端仍通过账号对应的模型服务推理。

```powershell
# 终端一，仅在本机开发验收时运行
python tools/codex_validation_bridge.py --timeout 240

# 终端二，DATABASE_URL 继续使用自己的开发数据库
$env:KNOWLEDGE_MODEL_PROVIDER = 'openai_compatible'
$env:KNOWLEDGE_MODEL_BASE_URL = 'http://127.0.0.1:18175/v1'
$env:KNOWLEDGE_MODEL_MODEL = 'codex-local'
$env:KNOWLEDGE_MODEL_REQUIRE_KEY = 'false'
$env:KNOWLEDGE_MODEL_TIMEOUT_SECONDS = '300'
python -m uvicorn knowledge.api:app --host 127.0.0.1 --port 8000
```

桥接仅监听 `127.0.0.1`，串行执行验收请求，不作为生产模型服务。输入、真实输出和 CLI 日志保存在 `.local/m1-codex-exchanges/`。生产部署设置外部服务地址、模型名称和密钥，无需安装 Codex 或启动桥接。官方用法见 [Codex 非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)。

## 页面操作

1. 选择项目，进入「项目知识」，点击「文档知识抽取」。原有左侧菜单保持不变。
2. 点击「登记原文并抽取」，填写「来源标识」「文档版本」「操作署名」。来源标识可填写 `urn:example:course:m1-requirements`。
3. 在「读取本地文档」选择 UTF-8 `.md`／`.txt` 文件，或直接粘贴到「原文内容」。可在「本轮抽取说明」明确关注范围。
4. 点击「登记原文并开始抽取」，等待状态变为「候选待审阅」。抽取期间不会写入正式知识。
5. 逐项核对候选名称、说明、知识类型、验收条件和原文证据。引文可查看原文高亮。逐字匹配只证明引文存在，仍需核对其是否支持候选含义。
6. 对于已有知识，核对「已有知识绑定」中的对象和固定版本。同一来源已经确认的稳定键不能更换身份。可以取消不应纳入本轮的候选，关系两端须同时保留。
7. 修正文字、验收条件、术语和引文。升级 M2 后先点击「分析本轮增量与影响」，逐项处理重复、冲突及缺失提示，再填写审阅依据并勾选已核对，建立提案。页面进入原有「项目提案」审阅页，详见 [M2 使用说明](m2-incremental-review.md)。
8. 点击「校验当前提案」。校验通过后检查修改前后内容，勾选确认，再点击「确认提交当前提案」。拒绝提案不会改变知识库；修改后可从同一抽取记录重新提出提案。
9. 返回「项目知识」，选择已提交的需求或规则，查看原文证据和历史版本。需要继续生成设计时，在「需求设计」创建流程并绑定刚确认的需求版本。

抽取记录提供「查看平台发送给模型的输入和模型回复」，可查看系统指令、固定上下文、Schema、模型真实答复，以及提示词版本和输入输出摘要。模型响应截断、结构无效或引文不匹配时，任务显示失败并保留可用交互记录。手工重试新建任务，不覆盖旧记录，也没有固定的五次生成限制。来源已更新时应选择最新来源再抽取。

## 原文与身份约束

- 原文来源按 URI 定位，各文档版本保存完整内容和 SHA-256。相同版本不可替换内容。普通原文登记最多 1 MiB，单次模型抽取最多 40000 个 Unicode 码点，超限明确拒绝。
- 模型提供逐字引文，服务端在固定原文中定位。唯一引文可以省略起始位置；多处重复时需扩大引文或明确 Unicode 码点起始位置。最终证据固定来源版本、摘要和左闭右开区间。
- 来源键对应稳定知识 ID，改名和修订内容不会更换已确认身份。同一名称不自动认定为同一对象；跨来源关联由人工显式选择已有知识。
- 新增、修订和证据写入与身份绑定在同一提案事务完成。实体类型、项目归属和所依据版本均受校验。重复确认已提交提案返回原结果。
- 需求验收条件使用稳定子项键，保存文本及原文证据，同时兼容现有文本验收条件字段。修订时沿用仍表示同一条件的键。
- 未选中或后续原文未出现的旧知识保持原状。模型不能据此自动删除或归档对象。
- 抽取任务固定当时的已有知识和项目基线版本。目标知识、关系或原文在审阅期间变化时，写入会拒绝过期版本。项目架构基线的参考版本被记录，抽取不修改架构基线。

M1 初版采用最多 200 条知识的完整上下文；升级 M2 后改为同来源身份优先的有界增量召回，具体配额及遗漏提示见 [M2 使用说明](m2-incremental-review.md)。候选上限仍为 40 条知识和 60 条关系，每项最多 5 处引文。

## 接口

| 方法 | 地址 | 行为 |
|---|---|---|
| POST | `/operations/source-snapshots` | 保存原文固定版本 |
| POST | `/extractions/projects/{project_id}/jobs` | 以 `source_id`、`source_version`、`actor` 和可选 `guidance` 发起任务 |
| GET | `/extractions/projects/{project_id}/jobs` | 分页查看任务及模型配置状态 |
| GET | `/extractions/jobs/{job_id}` | 查看固定原文、上下文、候选、模型问答和关联提案 |
| POST | `/extractions/jobs/{job_id}/proposals` | 以 `actor`、`reason`、审阅后的 `candidate` 形成不可变提案 |
| POST | `/operations/proposals/{id}/validate` | 事务试运行并保存校验结果 |
| POST | `/operations/proposals/{id}/commit` | 显式确认并原子提交 |
| POST | `/operations/proposals/{id}/reject` | 拒绝提案，保留历史 |

任务状态为排队、运行、成功、失败或输入过期。提案状态独立记录待审、已校验、已提交或已拒绝。任务成功只表示已有可审阅候选。

## 选课三轮验收

本机已完成的真实 Codex 调用、页面审阅、历史保留及测试结果见 [M1 选课验收记录](m1-acceptance-report.md)。

建议建立独立的「选课 M1 知识抽取验收」项目，使用同一来源标识，按下面顺序登记三个版本。已有选课教学项目及其三轮基线继续保留。

| 轮次与输入文件 | 核对重点 |
|---|---|
| v1 [基础选课](../examples/m1-course/01-基础选课.md) | 基础需求、学生和教学班术语、重复提交返回已有记录；容量等排除范围不能提取成当前已生效规则 |
| v1.1 [容量限制](../examples/m1-course/02-增加容量限制.md) | 旧需求沿用 ID，新增容量规则；容量为零拒绝、满员拒绝新学生、已选学生重复提交仍成功 |
| v1.2 [时间冲突](../examples/m1-course/03-增加时间冲突.md) | 保留容量约束，新增同一天时段重叠判断；相邻区间和不同星期几不冲突，重复请求不与自身冲突；错误优先级保留待确认 |

每轮先核对真实模型输出，再通过页面审阅提交。第二轮可将同一需求改名，确认 ID 不变且版本递增。第三轮完成后，回查 v1 和 v1.1 的知识、证据和原文，确认其仍显示当时内容。对错误引文、跨项目绑定、过期目标版本和来源被更新的提案，确认系统拒绝写入。

模型质量验收按人工核对记录计算，不能由格式通过率代替。将每条候选标为原文支持／不支持，并对文档中的预期规则逐项标记已覆盖／遗漏，分别计算准确率、召回率和证据支持率。自动化测试使用受控响应验证协议及边界；实际模型验收必须另外记录调用方式、模型追踪、真实输出和人工修订，不能把受控响应计为真实模型精度。

## 为图形差异准备的内容

项目模型的领域、模块、流程步骤和场景保留现有键。依赖、分支和时序消息增加可选稳定键，校验重复键。图输出附模型定位和固定知识引用，项目图附项目基线引用，设计图附设计流程及提案引用。结构化变更保存对象定位、前后内容、比较版本和需求／规则依据，支持辨认重命名、归属变化和明确的消息重排。

设计图的键属于 `design_snapshot` 作用域，结合设计流程 ID、流程版本与元素键定位；本轮尚未实现跨设计流程的自动身份匹配。历史无键的消息继续按场景比较。新增可选字段不改写历史原文、提案、实体或项目模型快照。本轮不交付图上变化叠加，不引入 Structurizr，也不宣称已支持完整 UML。后续阶段按[演进设计](knowledge-model-evolution.md)扩展。
