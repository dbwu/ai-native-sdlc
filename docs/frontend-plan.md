# 中文 SDLC 验证工作台实施计划

先通过页面验证前四阶段的实际操作，再继续阶段五的持续知识演进。首版工作台围绕“创建项目与流程、运行一个阶段、审阅变更、显式确认、查看测试与追溯”组织，复用现有后端状态机。

当前实施范围是本地参考模式：显式选择订单取消场景，使用确定性参考 Agent 生成产物，并真实运行内置 Python 测试。流程目标和标题用于记录这次验证，不会把任意业务描述自动变成相应代码。大模型、业务仓库、CI 和组织鉴权另行接入。

## 页面与操作

| 工作区 | 首版内容 | 验证目的 |
|---|---|---|
| 项目与流程入口 | 项目选择、新建项目、新建流程、流程状态列表 | 不需要填写 UUID 或手工准备 JSON |
| 四阶段工作区 | 需求、架构、实现、验证进度，当前步骤与可用动作 | 知道当前停在哪里，下一步为什么可做或不可做 |
| 产物查看 | 需求验收条件、组件与接口、数据模型、代码、测试内容 | 核对阶段实际产生了什么 |
| 提案审阅 | 原始版本与候选内容、校验结果、确认提交、拒绝及理由 | 用户亲自完成审核，校验不等于批准 |
| 测试与证据 | 实际测试数量、退出码、日志、内容摘要与执行 ID | 核对测试是否真的执行、证据是否属于当前版本 |
| 追溯与诊断 | 知识关系、阶段事件、任务尝试、冲突和阻塞原因 | 验证版本变化、失败恢复和历史保留 |

主界面采用项目选择与流程列表、四阶段进度、当前步骤操作卡和产物标签页。项目、流程、知识产物、执行证据和历史通过 Vue Router 分页导航，共用项目与流程选择状态。提案差异及详细历史可通过辅助面板打开，技术字段放入详情中，不占据主要操作区域。

## 实施顺序与验收

| 步骤 | 交付内容 | 验收标准 |
|---|---|---|
| 1 确定操作契约 | 核对现有接口、步骤与状态，明确需补接口 | 运行、校验、提交、任务完成和阶段放行不混为一个动作 |
| 2 页面基础与项目入口 | Vue 组件、路由导航、本地静态入口、中文布局、项目选择与创建、空状态 | 打开工作台可选择项目；页面可独立导航；服务不可用时显示原因与重试入口 |
| 3 流程创建与状态聚合 | 新建参考流程、当前阶段、当前任务和待审提案 | 页面自动关联业务身份，不要求输入 ID、版本号或租约 |
| 4 单阶段参考运行 | 服务端封装注册／复用 Agent、领取、上下文、执行与报告 | 每次只运行当前阶段并停在待审产物，不自动审批或推进 |
| 5 审阅与阶段门禁 | 按原始基线展示差异，提供校验、提交、拒绝、完成和放行 | 用户点击确认后才写入知识；校验失败不能表现为成功 |
| 6 真实测试与恢复 | 执行日志、知识追溯、暂停／恢复／取消／重试及历史 | 能看到四项真实测试和验证关系；失败与版本冲突有清晰恢复路径 |
| 7 浏览器验证与交付 | 页面联调、数据库回归、静态资源打包和使用说明 | 从新项目开始，完全通过页面完成参考闭环，保留全部审核历史 |

实施过程中先交付可识别、可操作的本地页面，再依据实际浏览器结果完善布局和异常交互。测试结果单独记录在验证记录中，不用计划中的验收标准代替已完成验证。

## 后端复用与最小补充

已有项目创建、知识查询、流程状态、任务、提案、门禁和测试执行机制继续复用，不在浏览器重写业务规则。

首版需要补充：

- **项目发现**：列出可选项目，解决现有实体查询必须先知道项目 ID 的问题。
- **流程快照**：聚合当前流程、任务、待审提案、产物、关系、执行记录和可用动作。
- **单阶段参考运行**：把原本仅能通过 Python 适配器调用的步骤提供给页面，停止在待审核状态。
- **提案差异**：以提案保存的原始基线读取旧版本，与候选内容比较，不用最新内容冒充原基线。
- **交互动作适配**：传递当前流程、任务和提案各自的版本，服务端完成原有状态检查；页面无需管理租约令牌。

这些适配调用现有服务层。界面根据服务端状态决定是否显示或禁用操作，最终许可仍由后端检查。

## 交互规则

“运行参考 Agent”产生候选产物；“校验”检查结构、语义和当前基线；“确认提交”写入知识；“完成任务”和“阶段放行”继续遵循既有独立条件。不会因为页面一次请求成功就跳过其他确认。

操作前记录本地署名和理由；它们用于追溯，不是登录认证。提案一经创建不可原地修改。拒绝或退回后保留旧记录，通过新的修订或阶段尝试继续。

请求期间阻止重复点击。遇到版本冲突时刷新并解释变化，由用户重新审阅，不自动替换版本号后重试写入。HTTP 200 中的校验失败或流程阻塞仍应以失败／待处理状态呈现。

暂停只停止流程推进，不表示已中断当前任务；取消会按原流程规则终止当前尚未结束的任务。重试可能先产生需要人工确认的关系对齐提案，页面需明确显示这一步。

## 技术与部署

首版使用 Vue 3、TypeScript、Vue Router 和 Vite，源码位于 `frontend/`，构建结果写入 `knowledge/web/`。通过组件拆分项目选择、阶段进度、动作卡、产物视图、提案审阅和执行证据，复用请求与状态处理，避免把多页逻辑堆入单个脚本。

路由采用 Hash 模式；入口仍为 `/workbench/`，页内导航位于 `#` 后，不占用既有后端 API 路由。构建后的页面与静态资源由现有 FastAPI 同源提供。Docker 镜像通过 Node 构建阶段生成页面资源，再由 Python 运行阶段提供服务；正常使用只需启动 Docker Compose，不要求另启前端开发服务。

前端开发时在 `frontend/` 中运行 `npm ci` 安装锁定依赖、`npm run build` 完成构建；构建产物随 Python 安装包和容器交付。修改页面源码后需重新构建，不直接维护 `knowledge/web/` 中生成的文件。该工作台保持本地部署，不把本地数据服务发布为云端站点。

前端负责展示、表单和交互；知识版本、提案审批条件、租约和流程推进规则继续由 Python 服务层管理。后续接入大模型、增加更复杂的交互或调整前端技术时，可复用这些 API 和状态边界。

## 本轮验证完成后的后续工作

先收集页面使用中的流程问题、字段缺口和错误恢复反馈。完成这轮体验验证后，再确定大模型与真实项目接入范围，并继续原计划的持续知识演进任务。

阶段五可在现有项目、流程、知识和提案页面上新增来源变化、影响分析与演进提案视图，无需把本轮页面作为一次性演示丢弃。
