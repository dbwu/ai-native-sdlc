# 第二阶段：知识操作

## 目标与范围

第二阶段把第一阶段知识模型连接到可追溯的输入和受控变更流程，形成以下闭环：

```text
调用方提供来源内容
  → 保存来源快照
  → 确定性解析结构化候选
  → 解析稳定标识并生成变更提案
  → 在事务中试运行现有语义校验
  → 显式提交或拒绝
  → 原子追加实体、关系及操作记录
```

来源内容与正式知识分开保存。采集不会直接把文本中的声明作为已验证事实写入知识库；提案校验也不等于批准。人工确认后提交时仍需重新执行适用的语义校验与并发检查。

本阶段沿用 Python、FastAPI、Pydantic、psycopg 和 PostgreSQL，不增加外部服务依赖。新增数据库结构通过后续 SQL 迁移建立，不修改已执行的第一阶段迁移。

## 来源与解析边界

采集入口接收调用方已经获取的内容和来源标识。URI 只作追溯地址，服务不会自动抓取网址、读取本地路径、执行代码或调用外部大模型。

支持结构化 JSON，以及 Markdown 中明确标注的 `knowledge-json` 代码块。解析器读取明确表达的实体与关系，不从任意自然语言中猜测需求、业务规则或代码语义。解析结果属于候选知识，需经过提案流程。

来源快照记录外部版本和内容摘要，保留后续重放及变更比较所需的信息。源内显式键用于维持知识身份，不使用标题、描述或内容相似度静默合并实体。更新知识时仍遵守第一阶段的稳定 ID、内容版本和生命周期规则。

来源身份由项目与 `source_uri` 确定。同一来源的 `source_revision` 再次提交相同原文和格式时返回既有提案，并标记 `replayed: true`；如果同一外部版本对应不同原文或格式，返回 409，调用方需提供新的外部版本。摘要基于原始 UTF-8 内容计算，因此仅调整 JSON 空白也属于原文变化。

稳定实体映射以来源内 `key` 为边界：同一来源的相同键复用既有实体；其他来源的同名键不自动合并。新身份在提案中分配，正式映射只有提案成功提交后才保存。未发生名称、描述或属性变化的实体不会为一次重复采集追加内容修订。既有实体发生变化时保留其当前生命周期状态，不把来源中的 `draft` 当作撤销已有状态的指令。

第一阶段直接创建仍使用 UUIDv4；采集产生的新实体使用来源身份作为命名空间，以 `entity:` 加来源键生成 UUIDv5。来源身份本身由服务生成并持久保存，因此同一来源键在试运行、提交和后续采集中保持一致。两种路径都使用与标题和文件路径无关的稳定 UUID。

从来源产生的修订使用 `inference` 来源性质，清空旧证据引用，防止把旧依据移用于新内容。关系适用版本或理由发生变化时，修订回到 `proposed` 并清空旧证据。若实体或关系内容没有语义变化，则保留原修订及其证据，不仅为记录新来源版本而改写正式知识。

来源中缺失的既有键会出现在提案的 `removed_keys` 提示中，不自动删除或归档知识。实体类型不能借由复用键静默改变；需要新的知识身份时应使用新的键。

### 结构化内容示例

```json
{
  "entities": [
    {
      "key": "REQ-001",
      "kind": "Requirement",
      "name": "支持订单取消",
      "attributes": {
        "acceptance_criteria": ["未支付订单可以取消"]
      }
    },
    {
      "key": "BR-001",
      "kind": "BusinessRule",
      "name": "支付前允许取消"
    }
  ],
  "relationships": [
    {
      "type": "DERIVED_FROM",
      "source_key": "REQ-001",
      "target_key": "BR-001",
      "rationale": "需求依据该业务规则提出"
    }
  ]
}
```

Markdown 来源把同样的 JSON 放入一个 `knowledge-json` 代码围栏。普通正文不会被自动抽取，也不能通过嵌套在其他代码块中的伪装围栏注入候选知识。

解析约束：

- UTF-8 编码内容最多 1 MiB；每批包含 1～100 个实体、0～200 条关系。
- `key` 最长 200 字符，区分大小写，可使用中文；任何位置的空白均会被拒绝，不自动去除首尾空白或合并身份。关系的 `source_key`、`target_key` 必须引用同批实体。
- `Project` 不可导入，采集目标项目必须预先存在。实体属性沿用第一阶段对应类型的校验规则，未定义字段会被拒绝。
- 候选实体使用 `draft`，候选关系使用 `proposed`；来源不能指定 `active` 或 `verified`，也不能注入正式知识 ID、来源追踪或证据引用字段。
- 重复键、重复关系、对称关系的反向重复、自关联、无效关系方向及包含／替代关系成环会被拒绝。

示例需求和业务规则仅说明输入格式，不代表系统为项目新增了这些业务要求。

## 提案与正式知识

提案保存候选变更及其依据。实体身份、关系语义、证据要求和生命周期校验复用第一阶段服务层，避免采集路径形成另一套较弱的写入规则。

提案计划一经创建不可原地修改。除了采集生成的提案，也可以为已有实体或关系提交完整修订计划，用于内容、证据或生命周期变更。修订计划必须携带第一阶段的 `expected_version`；同一提案不能多次修订同一个对象。需要调整候选计划时，保留原提案记录并创建新提案。

提案状态与事件版本独立于实体内容版本：

```text
pending（待校验）
  → 校验通过 → validated（校验通过）
  → 校验失败 → pending（保存失败结果）
pending / validated → rejected（已拒绝，终态）
validated → committed（已提交，终态）
```

每次校验、提交或拒绝携带提案事件的最新 `expected_version`。校验结果会追加审核事件，因此提交时应使用校验响应中的新提案版本。校验状态不代表已完成组织授权，也不会把候选知识性质升级为事实。

校验通过事务试运行检查整组变更，试运行结束后回滚，不留下正式实体、关系或修订。提交重新校验并在一个事务中写入整组变更；任意一项失败时全部回滚。已存在对象发生并发修改时，调用方应读取当前知识并重新协调，不允许无提示覆盖。

同一项目的操作复用项目级事务锁。正式对象版本与提案基线不一致，或来源在提案创建后已有更高快照版本时，校验／提交会报告冲突。此时需要重新采集或建立新的修订提案，不能只修改提交请求中的预期版本来绕过基线。对已成功提交的提案重复提交会返回原有结果并标记重放，不会重复追加知识修订。

第一阶段的直接写入 API 保留兼容，用于本地维护和已有客户端。第二阶段采集路径必须经过提案；这不是覆盖所有写入入口的组织级审批系统。

## HTTP 使用

所有新增接口位于 `/operations`。启动与依赖沿用项目使用说明；已有数据库先执行 `python -m knowledge.db` 应用新增迁移。可运行 `python -m knowledge.operations_demo` 查看合成演示，也可按下述步骤手动调用。

### 1. 采集并查看提案

先通过第一阶段接口创建 Project，再向 `POST /operations/ingestions` 提交：

```json
{
  "project_id": "<已存在项目的 UUID>",
  "source_uri": "urn:example:requirements",
  "source_revision": "v1",
  "format": "json",
  "content": "<JSON 示例文件的原始文本>",
  "actor": "本地维护者",
  "title": "订单取消知识采集（合成示例）"
}
```

`content` 是原始文本字符串，不是嵌套的 JSON 对象。可以将 `examples/phase2-source.json` 的 UTF-8 原文作为值；Markdown 使用 `format: "markdown"` 和 `examples/phase2-source.md` 原文。原文中的空白会保留。`title` 可省略，默认“采集知识变更提案”。

响应包含 `proposal` 和 `replayed`。查看 `proposal.plan.operations` 确认将创建或修订哪些对象，查看 `proposal.plan.entity_mapping` 中的稳定 ID 和预期内容版本，以及 `proposal.plan.removed_keys` 是否有需要处理的来源缺失项。此时尚未写入正式知识。

### 2. 试运行校验

向 `POST /operations/proposals/{proposal_id}/validate` 提交：

```json
{
  "expected_version": 1,
  "actor": "本地维护者",
  "reason": "核对该合成提案的结构、关系语义与当前基线"
}
```

这里的版本应取自刚读取的 `proposal.version`，不能固定假设永远为 1。响应的 `proposal.result.valid` 表示试运行是否通过；失败时检查 `errors`。校验失败也会追加事件，因此需重新读取提案版本再操作。

### 3. 显式提交或拒绝

确认计划与试运行结果后，向 `/operations/proposals/{proposal_id}/commit` 提交相同结构的审核请求，`expected_version` 使用校验响应中的最新 `proposal.version`，`reason` 说明提交依据。提交成功后状态为 `committed`，结果记录实际写入的 ID 和内容版本。

若不接受该计划，改向 `/operations/proposals/{proposal_id}/reject` 提交审核请求并说明理由。被拒绝的提案保留历史，不能原地改写；再次提交相同来源版本只会重放被拒绝的原提案，需要新的来源版本或手工提案。

### 4. 修订已有知识

`POST /operations/proposals` 接收已有对象的完整修订。例如将某草稿需求设为生效：

```json
{
  "project_id": "<项目 UUID>",
  "title": "确认需求生效",
  "actor": "本地维护者",
  "changes": [
    {
      "op": "update_entity",
      "id": "<已有需求 UUID>",
      "data": {
        "expected_version": 1,
        "name": "已审阅的需求名称",
        "description": "已审阅的完整说明",
        "status": "active",
        "attributes": {"acceptance_criteria": ["已确认的验收条件"]},
        "evidence": [],
        "provenance": {
          "actor": "本地维护者",
          "source_uri": "urn:example:review",
          "source_revision": "review-001",
          "change_reason": "核对后确认需求内容",
          "nature": "human_confirmed"
        }
      }
    }
  ]
}
```

`data` 必须包含希望保留的完整可变内容；省略可选值会采用第一阶段默认值。另一种操作为 `update_relationship`，其 `data` 使用第一阶段关系完整修订结构，包含两端版本、状态、依据、证据、来源追踪和 `expected_version`。一个手工提案最多 200 项变更，只支持已有对象修订；新建使用采集或第一阶段 API。手工提案同样经过校验及显式提交。

### 查询与错误

- `/operations/sources?project_id=…` 列出来源最新快照；`/operations/sources/{source_id}/versions/{version}` 读取原文和摘要。
- `/operations/proposals?project_id=…` 按创建时间从新到旧列出提案，可用 `status` 筛选。列表和审核历史支持 `limit`（1～200，默认 50）及 `offset`（默认 0）。
- `/operations/proposals/{id}` 返回不可变计划和最新事件；其 `/history` 子路由按版本从新到旧返回审核记录。
- 结构或语义无效通常为 422，不存在的记录为 404，并发基线、重复来源版本内容或无效提案状态为 409。试运行的业务校验失败通过 200 响应中的 `proposal.result.valid: false` 与错误列表表示，不能只检查 HTTP 状态码。
- 所有操作人字段仅作署名记录，不代表通过身份认证或组织授权。

## 只读分析

影响分析沿项目内显式关系寻找潜在受影响对象，给出传播依据和版本上下文，并限制搜索深度与结果规模。它表达“需要评估的候选影响”，不把关系可达性当作业务影响已经成立的证明。

传播仅使用当前为 `proposed` 或 `verified` 的关系：

| 关系 | 从变更实体向外传播的方向 |
|---|---|
| CONTAINS、IMPACTS | 按关系存储方向正向传播 |
| DEPENDS_ON、DERIVED_FROM、CONSTRAINED_BY | 反向传播到依赖方、派生方或受约束方 |
| IMPLEMENTED_BY、VERIFIED_BY、CONFLICTS_WITH | 双向追溯，提示关联对象需要复核 |
| SUPERSEDES | 反向传播：旧实体变化时，提示复核替代它的新实体 |

`max_depth` 默认为 4，范围 0～12；`max_nodes` 默认为 200，范围 1～1000，包含起始实体。算法去重防环，为每个候选提供一条确定的最短解释路径，路径记录关系身份、类型、状态、遍历方向和两端适用版本。只有实际存在因深度或节点上限而未遍历的候选时，才返回 `truncated: true`。读取使用同一数据库快照，避免混合并发变更前后的图谱状态。

一致性检查识别版本引用陈旧、实体状态变化、证据变化、显式冲突以及需求实现／验证链缺口。检查结果是供维护者处理的问题清单，不自动修改关系、弃用实体或撤销历史证据。

一致性检查的 `limit` 默认为 100，范围 1～1000；结果包含稳定问题代码和中文说明，仅在确有更多发现被截断时标记 `truncated`。

| 问题代码 | 含义 |
|---|---|
| STALE_ENDPOINT | 当前关系仍引用端点的旧内容版本 |
| INACTIVE_ENDPOINT | 关系端点当前已弃用或已归档 |
| STALE_EVIDENCE | 证据实体已有较新修订 |
| INACTIVE_EVIDENCE | 所引用证据当前不再生效 |
| UNQUALIFIED_EVIDENCE | 已验证关系的证据不再满足基本可信性质要求 |
| UNRESOLVED_CONFLICT | 当前仍存在待确认或已验证的显式冲突关系 |
| MISSING_IMPLEMENTATION | 生效需求缺少指向当前生效版本的已验证实现关系 |
| MISSING_VERIFICATION | 生效需求缺少指向当前生效版本的已验证验证关系 |

链路缺口依据通用关系规则判断，不代表业务需求必须采用某种实现或测试方案。证据新版本另行提示，不静默把旧关系升级到新证据。

## 待负责人确认的决策

- **身份与权限：** 采集者、确认者和提交者信息仍由调用方声明。谁有权确认哪些知识、是否需要分离提交人与确认人、哪些来源具有权威性，需由项目负责人明确后才能配置共享审批与访问控制。
- **解析与来源：** 当前使用显式结构化内容。接入 Git、需求平台、Wiki 或外部大模型前，需明确访问授权、数据范围、版本策略和内容保留规则。
- **分析策略：** 图关系传播及链路缺口检查是初始工程默认值。项目特定影响方向、测试覆盖标准和冲突优先级不能从通用模型自动推定。
- **生命周期：** 来源移除某项内容不自动等于删除或归档正式知识。自动撤销、批量迁移或替代策略需要单独决策。

## 本阶段仍不实现

不实现 Agent 注册、任务分发、编排、上下文包、自动 SDLC 工作流、向量检索、自然语言事实核验或外部源码分析。原始文档和代码仍以其来源系统为准，平台保存其追溯信息和正式知识之间的明确关系。
