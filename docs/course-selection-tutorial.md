# 从零建立选课系统知识并逐轮增加需求

页面版本已补齐：请优先按[通用流程与选课验证指南](phase4-enhancement.md)完成纯页面三轮演练。下文保留接口操作方法，用于理解知识版本和提案协议；其中旧版页面限制由新指南更新。

本教程以一个单学期选课系统为例，演练基础需求、容量限制和时间冲突三个版本，学习如何保留需求依据、设计、代码位置、测试定义与变更历史。

当前版本提供项目知识、提案、通用流程绑定与人工产物提交页面。选课教学适配器支持三轮实际代码和测试执行；流程必须明确选择执行方式，修改标题不会改变适配器。下面的接口操作可用于理解知识协议，完整页面演练请使用新指南。

## 先分清三个对象

| 对象 | 在哪里 | 它代表什么 |
|---|---|---|
| 工程知识工作台 | `/workbench/` | 管理工程项目与参考研发流程 |
| 选课项目的知识 | 项目知识、提案页面及通用接口 | 选课需求、规则、设计、代码规划和测试定义 |
| 学生实际使用的选课教学应用 | 选课流程完成后的“代码与测试”页面入口 | 课程列表、选课按钮、已选列表及独立 SQLite 教学数据库 |

在知识库登记 `DataModel`，不会自动创建学生、课程和选课业务表；登记 `CodeArtifact`，不会自动写入或运行代码；登记 `TestCase`，不会自动执行测试。

“项目知识”浏览整个项目，“阶段产物”和“知识追溯”浏览选中流程绑定的版本。导入知识并提交提案后，可选择通用流程和选课教学适配器建立对应流程。

## 教程业务假设

以下内容用于练习，并非已经替真实学校确认的业务要求。

- 使用预置学生身份，暂不实现注册、登录和学校统一认证。
- 只处理一个学期。学生选择的是“教学班”，而非只有课程名称的课程目录项。
- 同一学生对同一教学班最多有一条有效选课记录；重复请求返回已有结果，不新增记录。
- 教程不包含支付、先修课、学分上限、候补、退课和管理员排课。
- 容量表示一个教学班最多接收的有效选课人数，容量为 0 时不接收选课。
- 时间冲突版本使用同一学期、每周重复的课表；暂不处理单双周和日期例外。星期为 1～7，开始与结束节次都是闭区间：第 1～2 节与第 2～3 节冲突，第 1～2 节与第 3～4 节不冲突。

真实项目开始前，应确认身份、学期、教学班、重复请求、容量边界和时间区间这些定义。不要把教程假设作为未经确认的学校政策。

## 三轮版本与示例文件

| 版本 | 本轮新增内容 | 预期知识结果 |
|---|---|---|
| v1 | 浏览教学班、选课、查看已选、重复选课幂等 | 建立基础需求及其设计与测试定义 |
| v1.1 | 满额拒绝与并发防超卖 | 新增容量需求和规则，修订相关技术知识 |
| v1.2 | 已选教学班之间的时间冲突检查 | 新增时间需求和规则，修订课表及选课设计 |

每个版本有两份文件：

| 用途 | v1 | v1.1 | v1.2 |
|---|---|---|---|
| 便于阅读的知识全文 | [v1-knowledge.json](../examples/course-selection/v1-knowledge.json) | [v1.1-knowledge.json](../examples/course-selection/v1.1-knowledge.json) | [v1.2-knowledge.json](../examples/course-selection/v1.2-knowledge.json) |
| 可粘贴到采集接口的完整请求 | [v1-ingestion.json](../examples/course-selection/v1-ingestion.json) | [v1.1-ingestion.json](../examples/course-selection/v1.1-ingestion.json) | [v1.2-ingestion.json](../examples/course-selection/v1.2-ingestion.json) |

请求文件已经把知识全文转换成 `content` 字符串，无需手工处理 JSON 引号和换行。只需替换 `project_id` 占位文本，并按需要修改署名。

三轮必须使用同一个项目与同一个 `source_uri`，按顺序完成每一轮校验和提交，再进入下一轮。

## 第一轮 建立基础选课知识

### 1 创建独立项目

打开 [中文工作台](http://127.0.0.1:8000/workbench/)，点击项目选择器旁的“创建项目”，填写：

| 字段 | 示例 |
|---|---|
| 项目名称 | 校园选课系统（教程） |
| 项目说明 | 单学期选课知识演练，先实现基础选课，再增加容量限制和时间冲突检查。 |
| 操作署名 | 教程操作者 |

保存后应自动选中新项目。此时只有项目边界，还没有课程表、业务代码或学生选课页面。

建立选课流程时，选择“通用流程：绑定已有知识”和“选课教学适配器”，核对版本及绑定。下面先完成知识采集和提案练习，随后按新指南建立实际流程。

### 2 取得项目 ID

打开 [接口文档](http://127.0.0.1:8000/docs)，找到 `GET /workbench/projects`。

1. 展开接口，点击 `Try it out`。
2. 将 `limit` 填为 `200`，`offset` 填为 `0`。
3. 点击 `Execute`。
4. 在响应中找到名称为“校园选课系统（教程）”的记录，复制它的 `id`。

这是系统生成的项目 UUID，不需要自行编造。后续所有 `project_id` 都填这个值。

### 3 阅读基础知识内容

打开 `v1-knowledge.json`，其中包含：

| 稳定键 | 知识类型 | 需要你审阅的内容 |
|---|---|---|
| `DOMAIN-COURSE` | 领域 | 学期、教学班、选课等术语 |
| `REQ-ENROLL` | 需求 | 列表、选课、已选查询和重复请求验收条件 |
| `BR-UNIQUE` | 业务规则 | 同一学生与教学班组合只能有一条有效记录 |
| `COMP-ENROLL` | 架构组件 | 选课服务的职责 |
| `IF-ENROLL` | 接口 | 规划中的 HTTP 接口契约 |
| `DM-ENROLL` | 数据模型 | 学生、教学班与选课记录的结构及唯一约束 |
| `CODE-ENROLL` | 代码资产 | 规划中的实现文件位置；尚未实现 |
| `TEST-ENROLL` | 测试用例 | 将来需要执行的测试定义；尚未执行 |

这里的 `key` 是来源中的稳定身份，不是系统 UUID。以后修改名称或内容仍保留相同的 `key`。

基础验收可以这样读：学生能够浏览可选教学班；对有效教学班发出选课请求后，可在已选列表中找到它；重复请求不会产生第二条记录；不同学生的已选列表相互隔离。

### 4 采集 v1 并生成待审提案

打开 `v1-ingestion.json`，把 `project_id` 中的 `<替换为选课项目UUID>` 替换为第 2 步复制的真实 ID。

在接口文档中找到 `POST /operations/ingestions`，点击 `Try it out`，用修改后的文件内容替换请求体，再点击 `Execute`。

本轮关键字段为：

```text
source_uri      = urn:tutorial:course-selection:spec
source_revision = v1
format          = json
```

成功响应中，重点检查：

| 字段 | 预期含义 |
|---|---|
| `proposal.id` | 本轮提案 ID，后面校验和提交使用 |
| `proposal.version` | 提案当前事件版本，不是业务版本 v1 |
| `proposal.status` | `pending`，表示待校验 |
| `proposal.plan.operations` | 将创建的实体和关系 |
| `proposal.plan.entity_mapping` | 稳定键对应的系统 UUID 和候选内容版本 |
| `proposal.plan.removed_keys` | 本轮应为空数组 |

此时只是保存了来源与提案，正式知识还没有写入。

若要查看差异 JSON，可在接口文档调用 `GET /workbench/proposals/{proposal_id}/diff`，填入该提案 ID。响应的机器字段为英文，名称与正文可为中文。项目提案页也可直接打开普通采集提案并审阅差异。

### 5 校验提案

找到 `POST /operations/proposals/{proposal_id}/validate`，填入提案 ID，请求体为：

```json
{
  "expected_version": 1,
  "actor": "教程操作者",
  "reason": "已核对基础选课需求、术语、幂等规则及设计和测试定义，执行结构与关系校验。"
}
```

这里的 `1` 只是首次提案的常见示例；实际必须使用刚读到的 `proposal.version`。

只有同时看到 `proposal.status = validated` 和 `proposal.result.valid = true`，才进入下一步。HTTP 返回成功本身不表示所有检查通过。

### 6 明确确认提交

找到 `POST /operations/proposals/{proposal_id}/commit`，请求结构相同，但 `expected_version` 必须使用校验响应中的最新 `proposal.version`，理由可以写：

> 已核对本轮候选知识，确认作为选课系统的需求与设计草稿保存；代码和测试仍未实现或执行。

提交后应看到 `proposal.status = committed`。

**“提案已提交”表示候选内容正式保存为可追溯知识，不表示选课功能已经开发完成。** 采集得到的实体仍为 `draft`，来源性质为 `inference`，关系为 `proposed`；不会因为按了提交就自动变成已生效或已验证。

### 7 查询和核对第一轮结果

在接口文档调用：

| 接口 | 参数与用途 |
|---|---|
| `GET /entities` | 填 `project_id`，查看项目内知识；`limit` 可填 `200` |
| `GET /relationships` | 填 `project_id`，查看需求、规则、设计和测试的关系 |
| `GET /operations/sources` | 填 `project_id`，查看来源 v1 及原文摘要 |
| `GET /operations/proposals/{id}/history` | 查看本轮创建、校验和提交的署名与理由 |

知识文件包含 8 个实体，项目本身也是一个实体。因此独立新项目的实体查询通常返回 9 条记录。不要把多出来的 Project 当成重复导入。

关系阅读示例：

```text
选课需求 ──依据 DERIVED_FROM──→ 唯一选课规则
选课服务 ──依赖 DEPENDS_ON──→ 选课需求
选课需求 ──由其实现 IMPLEMENTED_BY──→ 规划中的代码资产
选课需求 ──由其验证 VERIFIED_BY──→ 测试用例定义
```

最后两条此时都只是 `proposed` 的规划关系，不能当作已经开发或测试通过的证据。

本轮完成标准：基础规则说得清楚、验收条件可以检查、设计和测试有明确对应关系、提案历史可查。不是“学生现在已经可以登录选课”。

## 第二轮 增加教学班容量限制

### 8 先写清新增需求

新增需求 `REQ-CAPACITY`：教学班只能接收规定人数，满额拒绝；同时争抢最后一个名额时也不能超额。

建议按以下数据审阅，而不只写一句“支持人数限制”：

| 场景 | 预期结果 |
|---|---|
| 容量 2，已有 1 人，新学生选课 | 成功，人数变为 2 |
| 容量 2，已有 2 人，新学生选课 | 拒绝，人数保持 2 |
| 容量 0 | 拒绝新选课 |
| 已选学生重复请求满额教学班 | 返回原选课结果，不增加人数 |
| 只剩 1 个名额，两名学生并发请求 | 只允许一人成功，总人数不超过容量 |

最后一个场景要求业务实现中的事务或其他并发控制。只在学生页面上显示“已满”不能保证正确；在知识库保存规则表达式也不会自动执行这个限制。

### 9 采集 v1.1

打开 `v1.1-ingestion.json`，替换为同一个选课项目 UUID。在 `POST /operations/ingestions` 中提交。

本轮必须保持相同的 `source_uri`，把外部来源版本改成 `v1.1`。文件已经包含全部旧实体与关系，并新增容量需求、容量规则和容量测试定义。

查看提案时应重点看到：

- 新增 `REQ-CAPACITY`、`BR-CAPACITY`、`TEST-CAPACITY`。
- 原来的 `REQ-ENROLL` 复用同一 UUID；内容未变时不必增加实体版本。
- 选课组件、接口、数据模型和代码规划按容量要求修订，同一稳定键仍对应原 UUID。
- 基础选课需求受到容量规则约束；设计、代码规划和测试定义关联新增需求。
- 与被修订实体相关的关系更新适用版本，不沿用旧版本而不提示。

### 10 再走校验和提交

重复第 5、6 步，使用本轮提案 ID 与每次响应的最新提案版本。

审核理由可以写：

> 已核对容量为零、满额、重复请求与最后名额并发四类边界，确认容量需求及关联设计和测试定义的修订。

提交后，来源中的实体总数为 11；独立项目连同 Project 通常共 12 条。基础需求保持原身份，新增容量需求拥有新身份，技术产物保留连续版本历史。

### 11 查看潜在影响与版本历史

从本轮 `entity_mapping` 找到 `REQ-CAPACITY` 对应的 `entity_id`。调用 `GET /operations/impact`：

```text
project_id = 选课项目 UUID
entity_id  = REQ-CAPACITY 对应的 UUID
max_depth  = 4
max_nodes  = 200
```

根据已建立的显式关系，可以看到选课服务、接口、数据模型、代码规划和相关测试等潜在影响，以及解释路径。具体范围取决于当前关系图和查询边界。

注意方向：`COMP-ENROLL DEPENDS_ON REQ-CAPACITY` 表示组件依赖容量需求，所以容量需求变化时应复核组件。不要为了凑出预期结果，任意建立没有依据的关系。

影响分析返回的是 `POTENTIAL_IMPACT`，只提示哪些知识可能需要复核，不会自动改代码、执行测试或完成新需求。

再调用 `GET /entities/{entity_id}/history`，比较 `COMP-ENROLL` 或 `DM-ENROLL` 的旧版本与新版本。本轮完成标准是新增需求可识别、既有身份保留、设计变化可解释、影响和历史可查。

## 第三轮 增加上课时间冲突检查

### 12 明确冲突的判定方法

新增需求 `REQ-TIME-CONFLICT`：学生选择新的教学班时，不能与其已有有效选课在同一星期发生节次重叠。

在本教程的闭区间假设下，两个时间段冲突的条件为：

```text
星期相同，并且 新开始节 <= 已选结束节，并且 已选开始节 <= 新结束节
```

一个教学班可能有多个上课时间段，任意一组时间段冲突就应拒绝。

| 已选教学班 | 新教学班 | 预期 |
|---|---|---|
| 周一第 1～2 节 | 周一第 2～3 节 | 拒绝，重叠第 2 节 |
| 周一第 1～2 节 | 周一第 3～4 节 | 允许，没有重叠 |
| 周一第 1～2 节 | 周二第 1～2 节 | 允许，星期不同 |
| 教学班每周有两个时间段 | 新班与其中一个时间段重叠 | 拒绝 |
| 对已经选过的同一教学班重复请求 | 返回原选课结果 | 不重复占名额，不把自身当成新的冲突 |

若学校使用时间戳、单双周、不同校区交通间隔等规则，需要另行修订模型与验收条件，不能直接沿用此教程假设。

### 13 采集、审阅和提交 v1.2

打开 `v1.2-ingestion.json`，仍使用同一项目 UUID 和来源地址，外部来源版本为 `v1.2`。

通过采集、校验、确认提交三个接口完成本轮。预期新增：

- `REQ-TIME-CONFLICT`：时间冲突需求。
- `BR-TIME-CONFLICT`：同星期闭区间冲突规则。
- `TEST-TIME-CONFLICT`：重叠、相邻、不同星期及多时间段测试定义。

技术知识中的教学班课表字段、组件检查职责、接口失败说明和代码规划会修订。已有基础与容量需求继续保留，不新建一个同名项目来替代原项目。

审核理由可以写：

> 已确认时间区间边界、多时间段和重复请求规则，并核对原有容量规则仍适用，确认本轮需求与关联技术知识。

提交后来源实体共 14 个，连同 Project 通常共 15 条。

### 14 完成一轮变更检查

1. 查询 `REQ-TIME-CONFLICT` 的潜在影响，检查是否覆盖相应设计、代码规划和测试。
2. 查询技术实体历史，比较 v1、v1.1、v1.2 的设计变化。
3. 查询关系，确认时间冲突需求有依据、实现规划和测试定义。
4. 调用 `GET /operations/consistency`，填项目 UUID，阅读陈旧引用、无效证据或链路缺口提示。
5. 列出尚未实现、尚未执行的工作，不把“没有发现项”当成业务正确性证明。

一致性检查也不是产品验收。特别是草稿知识可能尚未满足某些检查的适用条件；没有警告不证明代码存在，也不证明容量并发和时间冲突已经通过测试。

## 三轮之后如何进入真正编码和业务验收

### 现在已经得到的内容

你已经有可追溯的选课业务说明、三轮需求与规则、设计变化、代码规划、测试定义、来源版本和提案审核记录。这个底座可以作为开发输入。

### 仍需完成的开发工作

| 工作 | 具体结果 |
|---|---|
| 学生页面 | 教学班列表、选课按钮、已选教学班和失败原因 |
| 业务服务 | 实际选课与查询接口，实现幂等、容量控制及时间冲突检查 |
| 业务数据库 | 真正创建学生、教学班、课表、选课业务表及约束 |
| 代码接入 | 在开发仓库保存实现并记录真实提交版本或内容摘要 |
| 测试执行 | 实际运行测试，保留与代码版本匹配的日志与报告 |
| 知识回写 | 将代码、测试和证据通过新提案关联到准确需求版本 |

选课教学适配器已提供上述范围内的教学实现与独立测试，流程完成后可打开业务预览和下载源码。真实学校的扩展需求仍需开发；执行器只接受对应注册版本，不接收任意命令。

若由开发者人工实现，建议每轮使用相同的完成顺序：

```text
确认本轮需求与设计
→ 在业务仓库实现
→ 执行基础测试与本轮新增测试
→ 记录真实代码版本和测试证据
→ 提出知识修订提案
→ 校验并确认提交
→ 核对该需求对应的实现与验证关系
```

例如完成 v1.1 时，不能只跑“课程没满可以选”的正常路径，还要真实验证“最后一个名额的并发请求”及 v1 的重复请求行为。完成 v1.2 后，也要保留容量与幂等回归。

### 代码与证据怎样回写

这一步属于开发完成后的高级维护，不能用示例 UUID 或虚构测试结果代替。

1. 读取 `CODE-ENROLL` 当前实体，保留其稳定 ID，用真实仓库地址、路径、提交版本及说明提出 `update_entity` 修订。
2. 提案入口为 `POST /operations/proposals`，`changes[].data` 使用完整修订内容，并携带实体的当前 `expected_version`；不要只传一个修改字段。
3. 实际测试完成后，通过 `POST /entities` 登记新的 `Evidence`，或通过新的来源采集提出证据候选；已有证据的修订才使用 `POST /operations/proposals`。代码证据固定到代码实体版本；测试执行证据固定到测试实体版本，记录真实执行结果、报告定位和相匹配的内容摘要。直接创建接口属于现有维护入口，不自动代替提案审批。
4. 根据真实结果补充关系证据，并明确审阅生命周期、知识性质和关系状态。已验证关系必须满足现有语义要求，不能只改一个 `verified` 标记。
5. 每次业务内容修订后复核原证据的适用版本，不能用旧代码的通过记录证明新代码通过。

普通知识接口不会自动抓取 URI、核对远程 Git 提交或执行外部 CI，因此外部证据的真实性仍需要对应工具和人工复核。注册选课适配器提供本教程三轮代码的受控执行，外部业务仓库仍需独立执行适配。

## 常见问题

| 现象 | 应如何处理 |
|---|---|
| 选课项目中没有流程或通用产物列表 | 可从项目知识页浏览，并选择通用流程与选课适配器创建流程 |
| 修改项目名后仍生成订单代码 | 需在创建流程时明确选择执行适配器；名称不会改变所选适配器 |
| 同一个来源版本提交不同内容，返回 409 | 使用新的 `source_revision`，不要覆盖原版本 |
| 先提交 v1.2，再想提交尚未完成的 v1.1 提案 | 新来源快照会使旧提案过期；应顺序完成每轮，再进入下一轮 |
| 校验通过后提交仍提示版本冲突 | 使用最新提案事件版本；若知识基线已改变，重新协调并生成提案，不只改请求数字 |
| 同一需求导入后变成两个 UUID | 检查项目、`source_uri` 和大小写敏感的 `key` 是否改变 |
| 省略旧实体或关系，却没有被删除 | 来源缺失只作提示，不自动删除、归档或退役；本教程使用累计完整快照 |
| 增加容量字段被拒绝 | 领域字段放在数据模型结构或明确的扩展中，不随意添加核心类型未定义属性 |
| TestCase 已提交却没有测试结果 | 它只是测试定义，必须实际实现并执行测试才能产生执行证据 |

## 是否需要接入大模型

完成本教程的知识导入和三轮变更管理不需要大模型。开发者手工实现选课代码，或者使用专门的确定性适配器，也可以建立闭环。

如果目标是“输入自然语言选课需求，自动分析、设计、写代码并测试”，则需要进一步接入模型或其他生成执行方，以及通用需求页面、任务适配、业务仓库和受控测试工具。单独填写模型密钥不会使当前固定参考流程变成通用研发系统。

通用知识与提案页面、项目级知识浏览和选课教学执行支持现已补齐。先完成三轮页面验证，再继续阶段五的持续知识演进；自然语言驱动的任意业务生成仍需模型与执行适配。
