# 校园选课逐步验收 · 从新建需求到发布容量限制基线

本教程记录 2026 年 11 月 12 日在「校园选课 · 录屏模型验收」项目中的浏览器操作。先从零录入基础选课需求，完成设计并发布项目基线 v1，再增加教学班容量限制，完成增量设计并发布项目基线 v2。最后用「版本对照」查看两版图表。时间冲突、代码生成和业务测试执行属于后续工作。

## 开始前

- 打开工作台，确认服务已连接。复做时新建自己的练习项目。文中的工作台链接用于回看录屏项目，需能访问同一实例。 [打开工作台](http://127.0.0.1:8000/workbench/)
- **在「需求设计」核对「模型服务已配置」及模型标识。录屏使用本机兼容入口上的 `codex-local`。** 这是连接配置检查。首次实际生成完成后，在「模型生成记录」核对来源和原始回复。部署时按所在环境配置模型服务。 [模型服务配置](../requirements-design-guide.md#配置模型服务)
- Windows 录屏使用 `Win + Shift + R`，框选工作台浏览器区域并点击「开始」。计时出现后再操作。每段完成后保存录像，再由用户确认下一步。遇到宽图时先纵向滚到标题，再在图框内横向滚动以展示参与方、分支和结果。
- 加粗的模型操作涵盖发起调用和查看已保存回复。模型提出候选，平台校验结构及知识引用，人审阅后提交。Mermaid 根据结构化内容渲染图表。「版本对照」依据稳定标识比较两版内容。

## 01 新建项目与基础需求

1. 在工作台顶部点击「创建项目」。填写项目名称 `校园选课 · 录屏模型验收`，操作署名 `Codex 录屏验收`，说明可填「用可录制的工作台操作，从基础选课开始，逐轮验证容量限制和课表冲突的模型设计及图表。每个阶段完成后复核。」点击表单内的「创建项目」，核对顶部当前项目。
2. 点击「项目知识 → 新建知识」，类型选「需求」。名称填 `基础选课与重复提交`。说明录入以下正文。

   > 学生提交自己的有效学生标识和目标教学班标识。首次提交为该学生建立一条选课记录，并返回记录标识。相同学生对同一教学班重复提交时返回原记录。本轮只验证基础选课和重复提交。容量限制和课表冲突留到后续轮次。

3. 在「验收条件」中每行填写一条。「变更依据」可填「根据基础选课说明固定本轮验收范围」。

   - 首次提交有效学生和教学班组合，新增且只新增一条选课记录，并返回该记录标识。
   - 再次提交同一学生和教学班，返回同一个记录标识，该组合的记录数仍为一。

4. 点击「建立待审提案」。在「项目提案」填写审核依据「首次只建立一条记录，重复请求返回同一记录标识。本轮需求和两条验收条件一致。」点击「校验当前提案」，看到「校验通过」后勾选提交确认，点击「确认提交当前提案」。
5. 回到「项目知识」，在知识目录选「基础选课与重复提交 · v1」。打开「需求分析文档」，滚动展示正文和两条验收条件。提案显示「已提交」、需求可从知识页打开，即完成本段。 [基础需求分析文档](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/knowledge?requirement=53a29b8a-a4f1-5af2-8ae9-50408fb80887&version=1)

## 02 调用 Codex 生成基础设计

1. **在「需求设计」点击「新建需求设计流程」。流程名称填「第 1 轮 · 基础选课设计」，选择「基础选课与重复提交 · v1」，操作署名填「Codex 录屏验收」。设计目标写明首次提交与重复提交、组件职责、必要接口与协作、用例、代表性时序及测试计划。** 点击「创建需求设计流程」保存输入。
2. 展开「本轮固定的需求版本」，核对两条条件。填写操作依据，点击「确认需求并启动」。流程到「可以生成设计」。
3. **将操作依据补为「按已确认的基础选课范围生成设计，分析组件责任、必要的协作、用例和代表性时序。区分设计假设与已确认业务规则。」点击「按已确认范围生成设计」，滚动到「模型生成记录」查看「排队中 → 生成中 → 生成完成」。**

   **为何调用大模型**　把自然语言验收条件转换为可审阅的职责、接口、数据、交互与测试设计，并把事务和唯一约束等设计选择列为审阅内容。

4. **展开「查看发送给模型的输入和模型回复」，先看「平台发送给模型」的系统指令和本轮需求，再滚动到「模型回复平台」查看保存的原始 JSON。** 这里展示已保存的调用记录。
5. **滚动查看「模型生成的候选设计」及其用例图、职责图、协作图和两张时序图。** 录屏中模型给出「选课提交处理」与「选课记录持久化」两个逻辑组件。提交处理调用取得或创建记录接口。持久化按学生和教学班的组合原子处理，首次创建一条记录，重复提交返回原标识。
6. 核对首次提交、重复提交及同一组合并发提交的测试计划。流程显示「设计待审阅」后暂停，等用户确认提交。 [基础选课设计流程](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/design?flow=bd83f303-3393-4c71-9e24-73a58b5ee0ba)

## 03 校验、提交并确认基础设计

1. 在基础选课设计流程中展开「设计知识提案与差异 → 展开修改前与候选内容」，查看两个组件、接口、数据结构和测试计划。
2. 到「当前流程操作」填写依据，点击「校验设计提案」。状态显示「校验通过」后，填提交依据，勾选「我已核对当前需求、设计假设及提案差异」，点击「确认提交设计提案」。页面进入「设计已提交」。
3. 在「设计已提交」状态填写完成依据，再次勾选确认并点击「确认本轮设计完成」。核对「本轮设计已确认」。录屏中基础设计的确认流程事件版本为 v7。
4. 点击「查看本次设计产物」，打开基础需求 v1。到「项目知识」查看「设计文档」，滚动展示摘要、验收条件和图示。可通过「下载 Markdown」导出。基线生成入口可以打开，等用户确认后再发起下一段。 [基础设计文档及产物](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/knowledge?requirement=53a29b8a-a4f1-5af2-8ae9-50408fb80887&version=1&design=bd83f303-3393-4c71-9e24-73a58b5ee0ba)

## 04 调用 Codex 生成项目基线 v1

1. **打开「项目知识 → 项目架构与业务流程 → 建立项目基线提案 → 从已确认设计生成项目基线」。在「设计来源」选「第 1 轮 · 基础选课设计」，填写操作署名和本轮建模说明。点击「模型生成基线提案」，展示「正在处理提案。模型分析完成后会进入审阅页」。**

   **为何调用大模型**　将已确认的需求级设计组织成完整的项目级模型，提出领域归属、模块职责、内部调用和读写关系、跨模块流程及代表性场景。录屏使用模型分析入口。

2. 录屏中的首轮基线生成经历两次结构校验失败。复做时可直接在「本轮建模说明」给出最终约束。若已生成成功，可以直接进入候选审阅。

   | 录屏中的反馈 | 调整与调用目的 |
   | --- | --- |
   | 第一次，流程参与角色与架构模块使用了同一标识。 | **补充 `processes[].participants` 只列学生等外部角色，角色键与架构节点键互不重名。内部模块在 `nodes` 定义，流程和时序直接引用模块键。再次点击「模型生成基线提案」。为何再次调用大模型**　需要按正确的角色与模块边界重新组织流程端点。 |
   | 第二次，学生被列为内部协作关系的端点。 | **继续约束 `collaboration_links` 仅描述系统内部协作。调用或依赖连接模块与接口，读写指向已声明的数据对象。学生的交互留在业务流程和时序中。再次点击「模型生成基线提案」。为何再次调用大模型**　需要保留学生的业务交互，并在项目协作图中生成合法的内部关系。 |

3. 第三次生成通过结构检查，进入「项目提案」，显示项目架构与业务流程 v1「待校验」。**展开「查看发送给模型的输入和模型回复」，滚动原始回复，核对基线摘要、节点和流程。展开「预览模型生成的候选图表」，逐一选择逻辑结构、接口与协作、业务泳道图及两张时序图。**
4. 检查「选课」领域下的两个模块、调用取得或创建记录的接口、读取原记录与写入新记录的协作。泳道图区分首次创建、重复提交和并发创建冲突。两张时序图分别展示首次返回新标识与重复返回原标识。停在待校验提案，等用户确认发布。 [基线 v1 提案](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/proposals/f62ee3a3-eba0-44d6-9bdf-4fd86926efc9)

## 05 校验并发布项目基线 v1

1. 在「项目提案」打开项目架构与业务流程 v1。填写「审核依据」，写明已核对基础设计 v7、两个模块职责、内部调用和读写、首次与重复路径。点击「校验当前提案」。
2. 确认「校验通过」，勾选「我已阅读本次变更内容及依据，确认提交时会写入知识库」，点击「确认提交当前提案」。提案变为「已提交」。
3. 在「项目知识 → 项目架构与业务流程」的「项目基线版本」选择「基线 v1 · 基础选课 v1 项目基线」。页面显示基线 v1 的确认时间。**核对模型来源为 `codex-local`，设计来源为 v7。**
4. 打开「架构总览 → 逻辑结构」，展开选课领域查看两个模块及职责。切到「接口与协作」，查看提交处理调用内部接口、持久化读取和写入选课记录。
5. 打开「业务流程目录」，选提交选课流程，横向滚动泳道。再从「时序场景」分别查看「首次提交建立选课记录」「重复提交返回原选课记录标识」。本段结束时以 v1 作为下一轮的已发布基线。 [已发布的项目基线 v1](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/knowledge?baseline=1)

## 06 录入并提交教学班容量限制

1. 在同一个项目打开「项目知识 → 新建知识」。类型选「需求」，名称填 `教学班容量限制`，说明填以下正文。

   > 在基础选课与重复提交规则上增加教学班容量限制。每个教学班的容量为非负整数，新增选课成功后的记录数不得超过容量。满员或零容量时拒绝新增，已有选课记录与人数保持不变。已选学生重复提交同一教学班时，即使满员，仍返回原选课记录标识。本轮聚焦容量限制，时间冲突留到后续轮次。

2. 在「验收条件」每行填一条。「变更依据」填「在已发布的基础选课范围上补充容量约束，保留重复提交返回原记录的语义。」

   - 容量为 1 时，第一名学生成功；第二名未选学生被拒绝，记录数保持为 1。
   - 教学班满员后，首名学生重复提交仍返回原记录标识，记录数保持不变。
   - 容量为 0 时，任何首次提交均被拒绝，记录数仍为 0。
   - 两名未选学生同时争抢最后一个名额，至多一人成功，最终记录数不超过容量。

3. 点击「建立待审提案」。审核依据填写「核对容量上限、满员时重复提交、零容量拒绝及最后一个名额并发争抢。四条条件均可独立验收。」点击「校验当前提案」，通过后勾选确认并点「确认提交当前提案」。
4. 回到「项目知识」选「教学班容量限制 · v1」，打开「需求分析文档」，滚动核对正文及四条验收条件。停在需求已提交状态。 [容量限制需求分析文档](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/knowledge?requirement=2b046152-bd81-5f94-8708-e2d904be6824&version=1)

## 07 调用 Codex 生成容量限制设计

1. **打开「需求设计 → 新建需求设计流程」。名称填「第 2 轮 · 教学班容量限制设计」，勾选「基础选课与重复提交 · v1」和「教学班容量限制 · v1」。设计目标注明以已发布项目基线 v1 为对照、沿用已有稳定标识、覆盖四条容量条件，并保留基础选课的重复提交语义。**
2. 创建流程，展开「本轮固定的需求版本」。核对「查看本轮固定的项目基线 v1」和两条需求版本。填写操作依据并点击「确认需求并启动」。
3. **点击「按已确认范围生成设计」。滚动展示模型生成记录中的排队、生成和完成状态。展开「查看发送给模型的输入和模型回复」，核对请求包含固定的项目基线及两条需求，滚动展示 Codex 原始回复。**

   **为何调用大模型**　理解新增容量规则对已有职责、接口和流程的影响，提出并解释增量方案，检查已有记录优先返回、满员与零容量拒绝、并发争抢最后一个名额之间的关系。

4. **审阅候选职责图、协作图和三张业务时序图，核对模型给出的职责与事务边界。** 候选沿用原有两个模块。持久化模块按教学班在事务内加锁，先判断是否已有选课记录，组合缺失才判断余位。新增「教学班容量」数据模型，接口增加容量拒绝结果。
5. 在「设计知识提案与差异」展开修改前与候选内容，核对已有组件及接口的原知识版本和候选版本，查看新增的「教学班容量」数据模型。停在设计待审阅，等用户确认提交。 [容量限制设计流程](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/design?flow=82e7d767-6bfd-48d4-b0b0-529322535845)

## 09 确认容量限制设计并查看产物

1. 用户确认后，在「需求设计」打开「第 2 轮 · 教学班容量限制设计」，查看所用的基线 v1。若提案为「待校验」，填写操作依据并点击「校验设计提案」。确认「校验通过」，填写已核对四条验收条件、设计假设与提案差异的提交依据，勾选确认并点击「确认提交设计提案」。
2. 看到「设计已提交」后，再次填写完成依据并勾选确认，点击「确认本轮设计完成」。成功状态为「本轮设计已确认」，录屏中设计流程事件版本为 v8。
3. 展开「查看本次设计产物」，点击「教学班容量限制 · v1」。在「项目知识」核对需求版本 v1、已确认设计 v8 和参考项目基线 v1。滚动「本次设计产物」，查看两个组件、两个接口和选课记录 v2，以及教学班容量和本轮测试用例 v1。
4. 打开「设计文档」，滚动展示摘要、验收条件、Mermaid 图示、组件职责、接口契约、数据结构和测试计划。需要交付给设计人员时，可点击「下载 Markdown」。页面上的「草稿」是知识生命周期字段，设计流程的确认状态以「本轮设计已确认」为准。这里展示的是测试计划。 [容量限制设计文档及产物](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/knowledge?requirement=2b046152-bd81-5f94-8708-e2d904be6824&version=1&design=82e7d767-6bfd-48d4-b0b0-529322535845)

## 10 调用 Codex 生成项目基线 v2 候选

1. 打开「项目知识 → 项目架构与业务流程」。若页面正选中固定历史版，先将「项目基线版本」切到「最新（基线 v1）」，再展开「建立项目基线提案」。
2. **在「从已确认设计生成项目基线」里将「设计来源」选为「第 2 轮 · 教学班容量限制设计」。在「本轮建模说明」填入以下指引，再点击「模型生成基线提案」，展示「正在处理提案」。**

   > **以已发布的基础选课项目基线 v1 为对照，以本轮已确认的教学班容量限制设计为依据。沿用现有领域、模块、端口、流程、场景及消息的稳定标识，采用本轮已确认的同一知识新版本。请在完整基线候选中呈现教学班容量数据与协作，以及首次提交、满员时重复提交、零容量和并发争抢最后一个名额对现有流程的影响。保留未受影响的业务范围，标明可从设计追溯的变化。时间冲突留到后续轮次。**

   **为何调用大模型**　将已确认的容量增量合入完整项目模型，沿用已有对象并分析需要改动的协作关系、流程分支和时序消息。

3. **在 v2 候选提案页展开「查看发送给模型的输入和模型回复」，滚动查看原始回复中的基线摘要、节点稳定键和固定知识版本。展开「预览模型生成的候选图表」，选择「领域与一级模块」「项目接口与协作」、业务泳道图和四张时序图。**
4. 对照提案的「项目基线变更」。两个模块、两个接口和选课记录引用本轮已确认的知识 v2。新增教学班容量及其读取关系。泳道新增容量行加锁、余位判断和拒绝分支。时序更新首次成功和满员时的重复提交，新增满员或零容量拒绝、并发争抢最后一个名额两个场景。
5. 核对提案标题包含「项目架构与业务流程 v2」且状态为「待校验」。停在候选页，等用户确认是否发布。 [项目基线 v2 提案](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/proposals/c20aa8b4-dba9-4b8e-9a69-c21b018e2aa6)

## 11 校验、发布 v2 并对照 v1

1. 在「项目提案」打开基线 v2，填写审核依据，核对其来源为已发布基线 v1 和已确认容量设计。点击「校验当前提案」。看到「校验通过」后填写发布依据，勾选提交确认，点击「确认提交当前提案」。核对提案显示「已提交」。
2. 到「项目知识 → 项目架构与业务流程」，在「项目基线版本」明确选中 v2。核对页面的「项目基线 v2」及确认时间。标题沿用模型生成时的名称，发布结果以基线确认记录为准。 [已发布的项目基线 v2](http://127.0.0.1:8000/workbench/?preview=codex-architecture#/projects/c04a7c7d-30a5-49f1-a8a9-aa6c1880e4bc/knowledge?baseline=2)
3. 在「架构总览 → 逻辑结构」展开「选课」领域和模块，展示职责和知识 v2。切换「接口与协作」，滚动查看新增的「选课记录持久化 → 教学班容量」读取关系，以及更新后的记录读写依据。
4. 切到「业务流程目录」，选择「提交选课并取得记录标识或容量拒绝」。横向滚动泳道图，查看查找已有记录、余位判断和容量拒绝。到「时序场景」依次查看首次提交成功、满员重复提交、满员或零容量拒绝、并发争抢最后一个名额四张图。
5. 点击「版本对照」。旧版本选 v1，新版本选 v2，点击「变化叠加」。在「图表」中依次切换下列视图。

   | 图表 | 核对内容 |
   | --- | --- |
   | 项目架构图 | 领域说明及两个模块职责有修改标记，模块层级仍可追溯。 |
   | 接口与协作图 | 蓝色标记修改，绿色标记新增的教学班容量和读取关系。 |
   | 业务流程泳道图 | 点击「按原尺寸查看」并横向滚动，查看新增的锁、余位判断和拒绝路径。 |
   | 业务时序图 | 选择首次成功场景，查看加锁消息的新增标记，再点「左右对照」并排核对 v1 和 v2。切换到并发争抢场景，确认它只在 v2 出现。 |

6. 如需留档可点「下载对照 Markdown」。录屏结束时，浏览器停在基线 v2 的「版本对照 → 接口与协作图 → 变化叠加」，项目服务与数据保留。
